# ADR 0006. Собственный DNS: Knot, скрытый первичный, зона из Git

| | |
| --- | --- |
| Статус | Предложено; роль написана, на живом сервере НЕ проверялась |
| Дата | 2026-08-21 |
| Затрагивает | ADR 0003 (PKI, ACME), ADR 0004 (внешний вход) |
| Зона | `idp.mbrd.ru`, делегируется из `mbrd.ru` (обслуживается той же командой) |

---

## 1. Решение

**Knot DNS.** Конфигурация в YAML — читается на ревью так же, как остальные
манифесты проекта; `kzonecheck` и `knotc conf-check` дают проверку до
выкладки; RFC 2136 есть для динамической зоны; пакет лежит в архиве Ubuntu
и приходит через зеркало реестра, не требуя отдельного бинарника в
локальном репозитории.

BIND сделал бы то же самое и был бы верным выбором, если команда его уже
эксплуатирует: для системы нулевого уровня знакомство важнее элегантности.

PowerDNS отвергнут не как продукт, а как модель. Правда переехала бы в
базу, Git стал бы её копией, и понадобился бы согласователь с обнаружением
дрейфа. Этот проект на «два места хранения одного факта» наступал уже
несколько раз — адрес apiserver в values от прежнего стенда, адреса соседа
в Cluster Mesh, версии коллекций из метапакета. Причина каждый раз одна.

---

## 2. Топология

```
        Git ──render──►  ┌──────────────────┐
                          │ hidden primary   │ ◄── cert-manager (DDNS, зона acme)
   cert-manager ─DDNS──►  │  НЕ в NS-записях │
                          └────────┬─────────┘
                            NOTIFY │ AXFR/IXFR
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
            ┌───────────────┐             ┌───────────────┐
            │ secondary ДЦ1 │             │ secondary ДЦ2 │  ◄── это и есть NS
            └───────────────┘             └───────────────┘
```

**Высокая доступность встроена в протокол.** Резолвер сам идёт ко второму
NS, если первый молчит. Ни VIP, ни балансировщика, ни механизма
переключения строить не нужно — нужны два сервера в разных доменах отказа.

**Первичный скрыт намеренно.** Его нет в NS-записях, резолверы к нему не
ходят. Он может лежать сколько угодно: разрешение имён продолжается,
останавливаются только изменения. Это разделяет два разных по тяжести
отказа — «нельзя опубликовать запись» терпимо часами, «зона не отвечает»
неприемлемо.

Первичный не обслуживает внешние запросы вообще и может быть закрыт от
внешней сети целиком: ему нужны только выкладка из Git и DDNS изнутри.

---

## 3. Почему две зоны, а не одна

`idp.mbrd.ru` — **только из Git**, динамических обновлений не принимает.

`acme.idp.mbrd.ru` — **только динамическая**, в ней живут TXT-челленджи
ACME и ничего больше. В основной зоне для каждого имени лежит статический
CNAME:

```
_acme-challenge.foo.idp.mbrd.ru.  CNAME  foo.acme.idp.mbrd.ru.
```

Что это даёт:

* основная зона остаётся чистой функцией от Git, её никто не правит на ходу;
* ключ DDNS имеет власть **только** над зоной, где нет ничего, кроме
  челленджей: его компрометация не позволяет подменить записи сервисов;
* решение про wildcard-сертификат можно принять когда угодно — механизм
  уже готов, а если wildcard не понадобится, зона просто останется пустой.

Смешивать статику и динамику в одной зоне технически можно, но тогда либо
ключ обновления получает власть над всей зоной, либо приходится
замораживать зону на время выкладки. Оба варианта хуже одной лишней зоны.

---

## 4. Серийный номер SOA

Управляется **самим Knot** (`zonefile-load: difference` +
`serial-policy: increment`): при изменении файла зоны сервер сам увеличивает
серийник.

Это снимает проблему, которая была в первом варианте схемы, где два сервера
независимо рендерили зону из Git: одинаковое содержимое давало разные
серийники, и расхождение приходилось бы отлавливать вручную. Со скрытым
первичным авторитет один, и вопрос исчезает.

---

## 5. Ключи и права

Два разных ключа TSIG, и это не формальность:

| Ключ | Кому | Что разрешено |
| --- | --- | --- |
| `transfer` | вторичным серверам | AXFR/IXFR обеих зон |
| `acme-update` | cert-manager | UPDATE **только** зоны `acme.idp.mbrd.ru` |

ACL описывают ровно это. Передавать зону может только вторичный, обновлять
— только cert-manager и только свою зону.

---

## 6. Таймеры SOA

`expire` — единственный таймер, превращающий поломку репликации в отказ.
Пока он не истёк, вторичные отдают устаревшие данные, и это **правильно**:
устаревший ответ лучше отсутствующего. Ставится неделями, не часами. Иначе
сломавшаяся ночью передача зоны к утру даёт SERVFAIL по всей зоне.

`refresh` и `retry` страхуют на случай, если NOTIFY не дошёл; основную
работу делает NOTIFY.

---

## 7. Что проверять

| Что | Как | Ожидание |
| --- | --- | --- |
| разрешение имени | запрос к каждому NS | одинаковый ответ |
| **отказ одного вторичного** | погасить | разрешение продолжается |
| **отказ первичного** | погасить | разрешение продолжается; изменения и DNS-01 останавливаются — измерить запас по сроку сертификата |
| **сломанный ключ передачи** | испортить TSIG | вторичные отдают старое до `expire`, а не отваливаются сразу |
| права ключа DDNS | попытаться обновить им основную зону | отказ |
| битая запись | подсунуть в CI | отвергается до слияния, а не в бою |
| расхождение серийников | сравнить SOA на всех серверах | сходятся за минуты |

Последняя строка — единственный симптом, по которому сломанная репликация
вообще заметна, пока не истёк `expire`. Если делать только одну проверку в
мониторинге, делать надо эту.
