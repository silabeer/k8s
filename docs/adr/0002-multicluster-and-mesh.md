# ADR 0002. Связность между кластерами, шифрование трафика и service mesh

| | |
| --- | --- |
| Статус | Предложено |
| Дата | 2026-07-29 |
| Основание | Раздел 21.2 требует отдельного ADR для service mesh и для multi-cluster networking |
| Связан с | ADR 0001 (замена kube-proxy как условие Gateway API) |
| Источники | Документация Cilium 1.19.1; https://gateway-api.sigs.k8s.io/ |

---

## 1. Контекст

Планируются **два кластера в разных дата-центрах**. Сетевая связность
между ними есть, машины в одном VRF, но в разных VLAN.

Требования к трафику между сервисами, заявленные явно:

* сервисы разных кластеров видят друг друга;
* трафик шифруется в транзите;
* тома — только ReadWriteOnce, NFS и SMB не используются.

Требований к идентичности сервисов и к L7-управлению трафиком между ними
(канарейки по заголовкам, ретраи, circuit breaking) **не заявлено**.

Это важно зафиксировать буквально, потому что дальше всё решение опирается
именно на объём требований, а не на список возможностей.

---

## 2. Что решается

Три вопроса, которые легко склеить в один и получить лишнюю систему:

1. Связность и обнаружение сервисов между кластерами.
2. Шифрование трафика.
3. Service mesh: идентичность рабочих нагрузок и управление трафиком.

Третий пункт **не следует** из первых двух. Именно на этом месте обычно
появляется Istio там, где достаточно было двух строк конфигурации.

---

## 3. Решение

### 3.1. Service mesh не принимается

Заявленные требования — связность и шифрование — закрываются Cluster Mesh
и прозрачным шифрованием Cilium. Mesh как отдельный слой не вводится:
ни Istio, ни Linkerd, ни Cilium mutual authentication.

Обоснование по пунктам:

* **Идентичность сервисов не требуется.** Cilium mutual authentication в
  1.19 остаётся beta, рукопожатие вынесено за пределы соединения, и
  конфиденциальность всё равно обеспечивает WireGuard или IPsec, а не TLS
  на соединение. Вводить beta-механизм ради незаявленного требования
  неоправданно.
* **L7-управление трафиком между сервисами не требуется.** Это
  единственное, ради чего Istio давал бы существенный выигрыш, и цена —
  второй data plane рядом с Cilium.
* **GAMMA не становится драйвером.** Gateway API покрывает east-west
  (ADR 0001, раздел 1.1), и если бы mesh был нужен, выбор реализации
  Gateway API был бы частично выбором mesh. При заявленных требованиях
  этот довод не применяется — см. раздел 5.

**Что при этом НЕ теряется.** Отказ касается mesh как отдельного слоя, а
не межкластерного доступа и не L7-фильтрации:

| Возможность | Даёт | Цена |
| ----------- | ---- | ---- |
| доступ сервисов между кластерами | Cluster Mesh, раздел 3.3 | входит в решение |
| глобальные сервисы с балансировкой | Cluster Mesh | входит в решение |
| политики между кластерами, включая L7 | `CiliumNetworkPolicy` | ноль: `cilium-envoy` уже развёрнут |
| L7-управление трафиком east-west | Gateway API / GAMMA | замена kube-proxy, ADR 0001 |
| идентичность рабочих нагрузок | mutual authentication | beta, нужен SPIRE |

Отклоняются только две нижние строки — те, за которые платят.

**Условие пересмотра.** Решение отменяется, если появится хотя бы одно:
требование доказывать идентичность сервиса на уровне политики; требование
L7-управления трафиком между сервисами (канарейки по заголовкам, ретраи,
circuit breaking); требование per-connection TLS с сертификатом рабочей
нагрузки (аудит, регулятор).

Первые две строки таблицы возвращают к ADR 0001: L7-управление east-west
идёт через GAMMA, а тот требует замены kube-proxy. То есть «добавить mesh
позже» означает принять и это решение.

### 3.2. Шифрование — WireGuard

Прозрачное шифрование Cilium, режим WireGuard. Отдельных компонентов не
добавляет, включается значением в values.

Два условия жёсткие и вытекают из совместной работы с Cluster Mesh:

* **Шифрование включается во ВСЕХ кластерах.** Смешанный режим не
  поддерживается: кластер без шифрования в mesh не подключить.
* **UDP 51871 между узлами разных кластеров.** Для разных VLAN это прямое
  требование к спискам доступа, а не деталь реализации.

Публичные ключи между кластерами передаёт сам `clustermesh-apiserver` —
ручного обмена не требуется.

### 3.3. Связность — Cilium Cluster Mesh

Родной механизм используемого CNI. Каждый кластер сохраняет собственный
control plane; синхронизируется только состояние.

**Что это даёт по существу** — перечислено явно, потому что формулировка
«связность и обнаружение сервисов» слишком скупа и её легко прочитать как
«между кластерами ничего нельзя»:

* **Взаимный доступ сервисов между кластерами.** Под из ДЦ-A обращается к
  сервису в ДЦ-B напрямую.
* **Глобальные сервисы.** Аннотация `service.cilium.io/global: "true"` на
  Service с одинаковыми именем и namespace в обоих кластерах — Cilium
  балансирует между подами обоих. Аннотация
  `service.cilium.io/affinity` со значением `local` предпочитает локальные
  endpoint'ы, пока они есть; для разных ДЦ это существенно, иначе трафик
  ходит между площадками без нужды.
* **Политики между кластерами.** В `CiliumNetworkPolicy` доступна метка
  `io.cilium.k8s.policy.cluster`, правила пишутся с указанием кластера
  источника или назначения.
* **L7-политики.** Правила по HTTP-методам и путям в
  `CiliumNetworkPolicy` работают и между кластерами. Отдельного mesh не
  требуют: `cilium-envoy` входит в поставку CNI и уже развёрнут.

Именно поэтому раздел 3.1 отказывается от service mesh, а не от
межкластерного доступа: доступ обеспечивает Cluster Mesh.

Требования из документации Cilium, которые нужно выполнить:

| Требование | Что делать |
| ---------- | ---------- |
| одинаковый режим датаплейна во всех кластерах | ставить одним playbook, режим зафиксировать в inventory |
| PodCIDR не пересекаются и уникальны | схема адресации, раздел 3.4 |
| уникальные `cluster.name` и `cluster.id` (1–255) | переменная `cluster_id`, раздел 3.4 |
| IP-связность между узлами по InternalIP | есть по условию задачи |

**Режим датаплейна выбирается туннельным (VXLAN), а не native routing.**
При native routing требуется маршрутизируемость PodCIDR между кластерами и
`nativeRoutingCIDR`, покрывающий все кластеры разом; в туннельном режиме
достаточно связности между адресами узлов. Для двух ДЦ в разных VLAN это
разница между «работает по условию задачи» и «нужно согласовывать
маршрутизацию pod-сетей с сетевиками».

Фактический режим текущего стенда **подлежит проверке**: в values он не
задан явно, действует значение чарта по умолчанию.

### 3.4. Схема адресации и идентификаторы

Разводится **до** установки второго кластера: изменить PodCIDR
действующего кластера нельзя.

| Кластер | `cluster_id` | PodCIDR | ServiceCIDR |
| ------- | ------------ | ------- | ----------- |
| первый (ДЦ-A) | 1 | 10.100.0.0/16 | 10.101.0.0/16 |
| второй (ДЦ-B) | 2 | 10.110.0.0/16 | 10.111.0.0/16 |

**Где что живёт — уточнение к первоначальной формулировке.** ADR
предполагал ввести переменную `cluster_id` в inventory Ansible. При
реализации выяснилось, что это лишнее: values Cilium берутся из
GitOps-репозитория (`clusters/<cluster_name>/values/cilium.yaml`), и один и
тот же файл читают роль `cilium_bootstrap` и Argo CD. Второе место
хранения давало бы расхождение без выигрыша.

| Значение | Где задаётся |
| -------- | ------------ |
| `cluster.name`, `cluster.id` | values Cilium в GitOps-репозитории |
| `pod_network_cidr`, `service_network_cidr` | `group_vars` инвентаря Ansible |
| `cluster_name` (путь в GitOps, имена ресурсов) | `group_vars` инвентаря Ansible |

`cluster.id` — число 1–255, уникальное в mesh. CIDR до этого задавались
одним значением на все инвентари, поэтому склонированный inventory дал бы
совпадение и mesh не собрался бы; теперь они разведены по инвентарям.

### 3.5. Экспозиция control plane mesh

`clustermesh-apiserver` должен быть доступен соседнему кластеру.
Варианты и применимость:

| Способ | Когда применим |
| ------ | -------------- |
| LoadBalancer | лучший вариант, даёт стабильный адрес; нужен работающий провайдер LoadBalancer |
| NodePort | требует стабильных адресов узлов; при исчезновении узла mesh переподключается к другому |
| ClusterIP | требует маршрутизируемости ClusterIP между кластерами; только через Helm |

Для двух ДЦ на собственных ВМ адреса узлов стабильны, а провайдера
LoadBalancer в кластере пока нет — **NodePort**. К LoadBalancer перейти,
когда появится реализация (MetalLB либо балансировщик площадки).

### 3.6. Где живут секреты пары кластеров

Подключение обменивается CA и адресом endpoint соседа. Это секреты,
специфичные для **пары**, и в Git-репозиторий они не идут ни при каких
условиях: репозиторий публичный, а даже в приватном такие секреты
неуместны.

До появления секрет-бэкенда (OpenBao и External Secrets Operator, раздел
21.1) подключение выполняется вне GitOps, а факт подключения и его
параметры фиксируются в документации кластера. Это **осознанный временный
разрыв** в модели «всё из Git», и он должен быть закрыт вместе с OpenBao.

## 4. Последствия

**Положительные**

* Ни одного нового data plane: используется CNI, который уже стоит.
* Шифрование — одно значение в values, без sidecar и без beta-механизмов.
* Каждый кластер автономен: отказ связи между ДЦ не роняет ни один из них,
  теряется только межкластерное обнаружение сервисов.

**Отрицательные**

* Шифрование обязано быть включено во всех кластерах: подключить кластер
  без него нельзя, то есть включение WireGuard становится предусловием
  расширения mesh, а не отдельным улучшением.
* Требование к сети: UDP 51871 между узлами разных кластеров, плюс порты
  `clustermesh-apiserver`. В разных VLAN это согласование ACL.
* Подключение кластеров временно выпадает из GitOps (раздел 3.6).
* Туннельный режим добавляет накладные расходы на инкапсуляцию по
  сравнению с native routing.

**Нейтральные**

* Отказ от mesh фиксирует и отсутствие L7-политик между сервисами.
  Разграничение трафика остаётся на уровне L3/L4 через NetworkPolicy.

---

## 5. Что это меняет в ADR 0001

Довод раздела 1.1 ADR 0001 — «выбор реализации Gateway API есть частично
выбор mesh» — при заявленных требованиях **не применяется**: mesh не
принимается, east-west через GAMMA не нужен.

Следствие: выбор реализации Gateway API развязывается и решается по
собственным основаниям ADR 0001 — цена замены kube-proxy против второго
data plane для north-south. Реализации, умеющие только north-south
(Envoy Gateway, NGINX Gateway Fabric и прочие), перестают быть заведомо
проигрышными.

Ограничение socket-LB на NFS и SMB **снято условием задачи**: тома только
ReadWriteOnce. Один из двух доводов против замены kube-proxy отпадает.

## 6. План реализации

Порядок продиктован тем, что часть решений необратима после установки.

1. **Проверить режим датаплейна** действующего кластера и зафиксировать
   туннельный явно в inventory, а не полагаться на умолчание чарта.
2. **Включить WireGuard** на первом кластере и проверить, что трафик между
   узлами действительно шифруется. Делается на текущем стенде, ни от чего
   не зависит.
3. **Ввести `cluster_id`** и развести PodCIDR/ServiceCIDR по инвентарям
   согласно разделу 3.4. Для действующего кластера значения сохраняются;
   меняется только то, что они перестают быть общими.
4. **Согласовать сетевые требования** с сетевиками: UDP 51871 между узлами
   разных кластеров, порты `clustermesh-apiserver`.
5. **Поднять второй кластер** тем же playbook с собственным inventory.
6. **Соединить кластеры**, проверить `cilium-dbg status --all-clusters` и
   доступность глобального сервиса из обоих кластеров.

## 7. Как проверяется

| Что | Чем |
| --- | --- |
| шифрование включено | `cilium-dbg status` показывает WireGuard; трафик между узлами не читается снятым дампом |
| mesh собрался | `cilium-dbg status --all-clusters` в каждом кластере: соседний кластер виден, состояние синхронизации без ошибок |
| сервисы обнаруживаются | сервис с `service.cilium.io/global: "true"` отвечает из обоих кластеров |
| предпочтение локальных endpoint | с `affinity: local` трафик не уходит в соседний ДЦ, пока живы локальные поды |
| политики между кластерами | правило с `io.cilium.k8s.policy.cluster` действительно разрешает и запрещает |
| автономность | разрыв связи между ДЦ не роняет ни один кластер; после восстановления mesh сходится сам |

Проверять **изнутри пода**, а не с узла: обращение с узла идёт другим
путём и этот класс отказов не показывает (см. дефект 35 в `TEST-PLAN.md`).

## 8. Открытые вопросы

* Фактический режим датаплейна текущего кластера не проверен.
* Работает ли Cluster Mesh при `kubeProxyReplacement=false`. В списке
  требований документации он не упомянут, и наблюдение на стенде говорит в
  пользу того, что работает: Cilium программирует сервисы в BPF и без
  замены kube-proxy. Проверить до планирования второго кластера — если
  окажется, что нужен, ADR 0002 становится зависим от ADR 0001.
* Появится ли провайдер LoadBalancer — от этого зависит переход с NodePort.
* Сроки OpenBao: до него подключение кластеров живёт вне GitOps.
