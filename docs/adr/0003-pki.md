# ADR 0003. Иерархия PKI: офлайн-корень, интермедиаты, ACME и SPIRE

| | |
| --- | --- |
| Статус | Предложено |
| Дата | 2026-08-19 |
| Затрагивает | Разделы 22 (секреты), 26 (PKI), ADR 0002 (общий CA для mesh) |
| Заменяет | Выпуск общего CA в `93-secrets-bootstrap.yml` самоподписанным корнем |

---

## 1. Задача

Свести выпуск сертификатов контура к одной иерархии: офлайн-корень,
онлайновые интермедиаты, автоматический перевыпуск через ACME. Отдельно —
подчинить этой иерархии SPIRE, чтобы SVID рабочих нагрузок доходили
цепочкой до корпоративного корня.

**Чего задача НЕ включает.** PKI control plane Kubernetes остаётся за
kubeadm. Кластерный CA — внутреннее дело кластера, снаружи его никто не
проверяет, а подчинение внешнему PKI сделало бы восстановление кластера
зависимым от доступности этого PKI. Продление уже автоматизировано и
проверено (`renew-control-plane-certs.yml`).

---

## 2. Кто в контуре потребляет сертификаты

Их семь, и они разные по сроку жизни, способу перевыпуска и последствиям
отказа. Валить всех под один издатель нельзя — это главная причина, по
которой ниже три интермедиата, а не один.

| Потребитель | Что за сертификат | Кто перевыпускает сейчас |
| --- | --- | --- |
| control plane Kubernetes | apiserver, etcd, front-proxy | kubeadm, playbook продления |
| kubelet | serving-сертификат | CSR + `kubelet-csr-approver` |
| `cilium-ca` | общий CA: Cluster Mesh, Hubble, mutual auth | `93-secrets-bootstrap.yml`, самоподписанный |
| SPIRE | CA для SVID рабочих нагрузок | сам SPIRE, самоподписанный |
| OpenBao | TLS его собственного слушателя | роль `openbao`, самоподписанный |
| Реестр артефактов | TLS Caddy | внутренний CA Caddy |
| Gateway API | сертификаты входа | cert-manager, на стенде самоподписанный |

Последние пять — кандидаты на переезд в новую иерархию. Первые два
остаются как есть.

## 3. Схема

```
              ┌──────────────────────────────┐
              │  Корень (офлайн, вне сети)   │   20 лет, включается только
              │  self-signed, P-384          │   для подписи интермедиатов
              └───────────────┬──────────────┘
                              │  sign-intermediate (вручную, по регламенту)
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
┌───────▼────────┐   ┌────────▼────────┐   ┌────────▼────────┐
│  pki_infra     │   │  pki_identity   │   │  pki_cilium     │   OpenBao,
│  3 года        │   │  3 года         │   │  3 года         │   отдельные
│  ACME включён  │   │  без ACME       │   │  без ACME       │   mount'ы
└───────┬────────┘   └────────┬────────┘   └────────┬────────┘
        │                     │                     │
        │ ACME (RFC 8555)     │ UpstreamAuthority   │ cert-manager Issuer
        │                     │                     │
   ┌────▼─────┐         ┌─────▼──────┐         ┌────▼─────┐
   │ реестр   │         │   SPIRE    │         │cilium-ca │
   │ OpenBao  │         │ интермедиат│         │ (общий   │
   │ Gateway  │         │            │         │ для mesh)│
   └──────────┘         └─────┬──────┘         └──────────┘
                              │ SVID
                        ┌─────▼──────┐
                        │  рабочие   │
                        │  нагрузки  │
                        └────────────┘
```

### 3.1. Почему три интермедиата, а не один

Разный радиус поражения и разный темп. `pki_infra` выдаёт сотни коротких
листовых сертификатов автоматически — это самый «горячий» и самый
уязвимый путь. `pki_identity` подписывает ровно один сертификат в
несколько месяцев — промежуточный CA для SPIRE. `pki_cilium` — один CA на
весь mesh, менять его больно.

Один общий интермедиат означал бы, что его компрометация или отзыв
задевает всё сразу, а политика доступа в OpenBao (она задаётся на mount)
не может быть разной для ACME-клиента и для SPIRE. Разделение стоит
дёшево: три mount'а вместо одного.

### 3.2. Почему ACME только в `pki_infra`

ACME — механизм для тех, кто умеет сам себя обслуживать: Caddy у реестра
и cert-manager в кластерах. Промежуточные CA так не выдают: у ACME нет
понятия «выдать CA», и не должно быть.

### 3.3. SPIRE

`UpstreamAuthority "vault"` обращается к PKI-движку и получает
**промежуточный** сертификат для собственного CA. Дальше SPIRE работает
как раньше — сам ротирует свой CA, сам держит bundle, — но выданные им
SVID проверяются цепочкой до корпоративного корня.

Это и решает открытый вопрос плана (раздел 6.4): mutual authentication
через границу кластеров требует **общего домена доверия**. С внешним
SPIRE, подчинённым общему корню, оба кластера получают идентичности из
одного источника, и вопрос «федерация или общий домен» снимается — общий
домен.

## 4. Порядок развёртывания и проблема курицы с яйцом

Три места, где зависимость кольцевая. Их надо назвать заранее, иначе они
всплывут посреди установки.

1. **TLS самого OpenBao не может прийти из ACME OpenBao.** Пока OpenBao
   не запущен, выдать ему сертификат некому. Решение: старт с
   самоподписанным (как сейчас), затем перевыпуск из `pki_infra` и
   перезапуск слушателя. Побочная польза: уходит дефект 65 — узлам
   раздаётся корпоративный корень, а не самоподписанный сертификат
   сервера, у которого нет `keyCertSign`.

2. **cert-manager живёт в кластере, который ещё не установлен.**
   Сертификаты Gateway API появляются только после установки кластера, и
   это нормально: до неё они не нужны.

3. **Реестру нужен сертификат до установки кластеров, а ACME-клиент у
   него свой (Caddy).** Значит `pki_infra` и ACME должны работать раньше
   реестра.

Отсюда порядок:

```
корень (офлайн) → интермедиаты в OpenBao → ACME в pki_infra
   → перевыпуск TLS OpenBao → реестр (Caddy берёт сертификат по ACME)
   → SPIRE (UpstreamAuthority) → кластеры → cert-manager → Gateway
```

## 5. Перевыпуск

| Что | Срок | Кто перевыпускает |
| --- | --- | --- |
| Корень | 20 лет | человек, по регламенту, офлайн |
| Интермедиаты | 3 года | человек раз в ~2 года, с перекрытием |
| SPIRE-интермедиат | недели | SPIRE сам, через UpstreamAuthority |
| Листовые (реестр, Gateway) | 90 дней и меньше | ACME-клиент сам |
| SVID | часы | SPIRE сам |

**Перекрытие интермедиатов обязательно.** Новый выпускается до истечения
старого, оба лежат в bundle доверия, пока не истекут все выданные под
старым листовые. Без перекрытия момент замены превращается в отказ всего,
что было выдано раньше.

---

## 6. Раздача доверия

Корпоративный корень нужен всем и раздаётся ровно так же, как сейчас
раздаётся сертификат реестра: задачей `Install the contour CA certificate`
в роли `os_prepare` — в системное хранилище узла — и отдельно в
`hosts.toml` для containerd. Переменная переименовывается из
`registry_ca_cert` в `contour_root_ca`: с появлением иерархии сертификат
перестаёт быть «сертификатом реестра».

В кластерах корень раздаётся ConfigMap'ом, который монтируют потребители;
bundle SPIRE распространяется самим SPIRE.

---

## 7. Риски и что проверить до внедрения

**Главное допущение, которое надо проверить первым.** Плагин
`UpstreamAuthority "vault"` написан под HashiCorp Vault. OpenBao —
форк Vault 1.14 и совместим по API, но **совместимость именно этого
плагина не проверена**. Если она не подтвердится, остаются два пути:
плагин `cert-manager` (тогда cert-manager становится посредником) или
`disk` с ручной подачей интермедиата (тогда теряется автоматическая
ротация). Проверять до того, как схема будет заложена в роли.

**Второе допущение.** ACME в PKI-движке OpenBao требует настроенного
`config/cluster` и включённой опции на mount'е. Наличие ACME
подтверждено документацией, точный набор параметров — нет.

**OpenBao становится системой нулевого уровня.** Сейчас это одна
незарезервированная ВМ, которая после перезагрузки запечатывается и ждёт
человека с ключами. В предлагаемой схеме от неё зависит выпуск всех
сертификатов контура. Пока она в таком виде — это единственная точка
отказа, и её резервирование должно идти в одном пакете с этой схемой.
Отказ не мгновенный: уже выданные сертификаты работают до истечения, то
есть запас равен самому короткому TTL — у SVID это часы.

**Что проверять на стенде:**

| Что | Чем |
| --- | --- |
| цепочка у каждого потребителя | `openssl verify -CAfile root.crt` до корня |
| ACME действительно перевыпускает | короткий TTL, дождаться обновления, сверить серийный номер |
| SPIRE получил интермедиат | SVID содержит цепочку из трёх звеньев, а не двух |
| mutual auth через границу | политика `authentication.mode: required` на глобальный сервис, обращение из соседнего кластера |
| **отказной путь** | сертификат, подписанный другим интермедиатом, отвергается |
| kubeadm не затронут | отпечаток кластерного CA до и после совпадает |
| поведение при недоступном OpenBao | что перестаёт работать и через сколько — измерить, а не предположить |

Последние два пункта обязательны: без них проверено, что схема работает,
но не проверено, что она ничего не сломала и что отказ предсказуем.
