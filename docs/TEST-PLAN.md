Обновление выполнено по процедуре раздела 27: сверена матрица
совместимости, CNI обновлён отдельно через GitOps (Cilium 1.19.6
заявляет только 1.31–1.34, поэтому потребовался переход на 1.20).
Шлюз `compatibility_matrix_verified` проверен: без подтверждения
обновление не стартует.

Ротация ключа шифрования etcd прослежена по префиксу записи в etcd на
каждой фазе:

| Фаза | Конфиг apiserver | Префикс в etcd |
| ---- | ---------------- | -------------- |
| до | `key1` | `key1` |
| 1 | `key1, key2` | `key1` — пишем старым, читаем обоими |
| 2 | `key2, key1` | `key1` — пишем новым |
| 3 | `key2, key1` | `key2` — все 12 объектов перешифрованы |
| 4 | `key2` | `key2` |

Секрет, записанный до ротации, читается после её завершения.

Восстановление проверялось так, чтобы отличить настоящий откат от
видимости работы: после снятия снимка создавались объекты, которых в нём
заведомо нет, и проверялось их исчезновение.

| Объект, созданный после снимка | После восстановления |
| ------------------------------ | -------------------- |
| `ns/after-snapshot` | `NotFound` |
| `cm/restore-canary` | `NotFound` |
| `secret/secret-canary` | `NotFound` |
| `podinfo` увеличен до 4 реплик | вернулся к 2 — значению из снимка |

Состояние на момент снимка уцелело полностью: семь namespace, 11 секретов,
Argo CD Application, рабочие нагрузки. Зашифрованный Secret читается —
ключ и его имя совпали с теми, которыми снимок записан. После
восстановления кластер принимает запись, новые Secrets шифруются.

Три члена etcd стартовали как новый кластер и здоровы; все четыре узла
`Ready`, посторонних подов нет. Прежний каталог данных сохранён на каждом
узле как `member.pre-restore-*`.

Второе восстановление выполнялось для проверки исправления дефекта 35:
кластер откатился, доступ к API изнутри пода работал сразу, Argo CD
продолжил реконсиляцию без ручного вмешательства.

Восстановление одного члена из снимка невозможно: два остальных сохранят
прежнюю историю и отвергнут его. Поэтому снимок разворачивается на всех
узлах разом, а `serial` в этом playbook недопустим — нужен барьер, который
даёт линейная стратегия.

Резервное копирование проверялось с временно укороченным интервалом:
таймер сработал многократно, снимки прошли `etcdutl snapshot status`
(877 ключей, ревизия 8303). `RandomizedDelaySec` разводит узлы по времени,
одновременных снимков нет. После проверки расписание возвращено к штатному.

**Замечание, не дефект:** снимок пишется в каталог данных etcd и только
затем переносится в каталог резервных копий — иначе файл не вынести из
контейнера, туда смонтирован hostPath. На стенде каталоги на одном разделе;
при отдельном диске под etcd (раздел 5.2) снимок временно занимает место
на самом критичном томе. Стоит следить за свободным местом.

### 3.5. GitOps

### 4.5. Из обязательного списка компонентов (раздел 21.1)

Установлено и проверено функционально: CNI, Argo CD, PriorityClass,
kubelet-csr-approver, cert-manager, default StorageClass, metrics-server.
Проверялись не по статусу пода, а по результату: `kubectl top` отдаёт
метрики, PVC связывается и под пишет в том, cert-manager выпускает
сертификат, Pending-CSR не остаётся.

Остаётся: External Secrets Operator, ingress или Gateway API,
observability-агенты, policy engine, etcd-backup CronJob, базовые
NetworkPolicy, ResourceQuota, LimitRange, PodDisruptionBudget.

Секрет-бэкенд закрыт: OpenBao развёрнут, путь `secret_backend: openbao`
пройден вживую на двух кластерах. Аутентификация и доверие к сертификату
передаются переменными окружения `ANSIBLE_HASHI_VAULT_TOKEN` и
`ANSIBLE_HASHI_VAULT_CA_CERT` — роли вызывают lookup только с `url`.

StorageClass на стенде — local-path-provisioner: том живёт на диске
конкретного узла и не переживает его потерю. Для production заменяется
на CSI облака.

PodDisruptionBudget не заводился намеренно: при одной реплике PDB с
minAvailable: 1 блокирует вытеснение и ломает вывод узла. Он появляется
вместе со вторым worker-узлом.

## 5. Дефекты, найденные прогонами

Сгруппированы по тому, чем именно обнаружены. Ни один не виден линтерам.

### 5.1. Контейнерные сценарии (удалены из проекта)

1. `provisioner.inventory.links` полностью отключает inline `host_vars`
   и `group_vars` — все 14 сценариев работали без своих переменных.
2. `ANSIBLE_ROLES_PATH` не задавался — роль не находилась по имени.
3. `privileged: false` (из примера в документе) — systemd в контейнере
   не стартует вообще.
4. `chronyd -Q` как валидатор конфига не проверяет синтаксис, а опрашивает
   NTP-серверы и ждёт: при недоступном NTP `os_prepare` висел бесконечно.
5. Каталог `/etc/systemd/journald.conf.d` не создавался перед записью.
6. `logrotate` настраивался, но не устанавливался.
7. `| first` по пустой последовательности ронял задачу на рендере
   `fail_msg`, пряча настоящую причину.
8. `groups['all']` включает `localhost` провижнера без `node_ip`.
9. `: ` внутри незакавыченного условия `assert` делает его отображением.

### 5.2. Первый прогон на ВМ

10. `validate:` модуля `template` неприменим к chronyd на Ubuntu:
    AppArmor запрещает читать временный файл даже под root.
11. `trim_blocks` съедает перевод строки после Jinja-комментария —
    отступ склеивается со следующей строкой, YAML ломается.
12. Проверка ключа шифрования через `| b64decode | length` отвергала
    **валидные** ключи: фильтр возвращает текст, и случайные байты дают
    неверную длину.
13. Роль `containerd` проверяла себя через `crictl`, который приезжает
    на следующем этапе.
14. `python3-kubernetes` нигде не устанавливался, хотя модули
    `kubernetes.core` выполняются на control-plane узле.
15. Межролевые ссылки на переменные: defaults одной роли не видны другой.
16. `\\s` в свёрнутом скаляре YAML остаётся двумя символами.
17. Рассогласование labels между шаблоном join и проверкой.
18. `no_log` на проверках формата скрывал причину отказа.

### 5.3. Конфигурации, которые роли не допускали

19. Порочный круг с hostname: preflight требовал того, что исправляет
    `os_prepare` на следующем этапе.
20. `gitops.repo_url` требовался на этапе 00, хотя нужен этапам 50 и 60 —
    запрещало поэтапное развёртывание.
21. `api_vip_managed: false` смешивал два разных случая: внешний LB и
    endpoint на самом узле кластера.
22. Деплой-ключ требовался безусловно — публичный репозиторий по HTTPS
    не поддерживался.

### 5.4. Валидация

23. Проверка шифрования затягивала в переменную двоичное значение из etcd.
24. Путь тестового образа собирался как `registry_host + /k8s/` — верно
    только для зеркала в Harbor.

### 5.5. Обслуживание

25. `add-node` использовал `--limit`, что ломало межузловые проверки
    preflight: факты остальных узлов не собирались.
26. `remove-node` удалял объект Node до `kubeadm reset` — kubelet мог
    перерегистрировать узел.
27. Возврат манифестов не был в `always`: при таймауте play прерывался
    с манифестами вне каталога.
28. **Секция `always` не выполняется, когда файл включается из handler.**
    Воспроизведено дважды: control plane оставался лежать. Тот же файл,
    включённый обычной задачей, отрабатывает целиком.

### 5.6. Ротация ключа шифрования и резервное копирование

Найдены вторым полным прогоном на чистых ВМ.

31. **Ротация не стартовала ни при каком состоянии ключа**, если бэкенд
    не OpenBao. `fail_msg` безусловно ссылался на `openbao_cluster_path`,
    а Ansible вычисляет аргументы задачи ДО проверки условий: при
    `secret_backend: vault_file` переменная не определена, и assert падал,
    даже когда ключ корректен. `no_log` на этой задаче прятал причину.
32. **`run_once` при `serial` выполняется раз на ПАРТИЮ, а не раз на play.**
    При `serial: 1` каждый узел — своя партия, поэтому перешифровка всех
    Secrets запускалась на каждом control-plane узле. Помимо лишней работы
    это гонка: параллельные `kubectl replace` дают конфликт
    `resourceVersion`, а `any_errors_fatal` обрывает ротацию посередине.
33. **Финальная инструкция самого playbook приводила к потере доступа ко
    всем Secrets.** Имя ключа было зашито константой `key1`, а ротация
    оставляет данные под именем `key2`. Выполнение инструкции «повысить
    ключ в бэкенде» приводило к тому, что следующий штатный прогон
    `40-control-plane-init.yml` отдавал apiserver верный ключ под чужим
    именем. Проверено изолированно на одном узле, ответ apiserver:
    `no matching key was found for the provided Secretbox transformer`.
    Имя ключа теперь хранится в секрет-бэкенде рядом с самим ключом,
    ротация чередует `key1 ⇄ key2` (жёсткий переход ломался бы уже на
    второй ротации), инструкция фазы 4 требует обновить оба поля.
34. **`80-backup.yml` падал на всех узлах, кроме первого**: роль писала
    референсный манифест CronJob в `/etc/kubernetes/bootstrap`, а этот
    каталог создают bootstrap-роли, выполняемые только на первом
    control-plane узле. systemd timer на остальных узлах не настраивался.

### 5.7. Балансировщик API endpoint

Найдены при первой установке с выделенным LB. До неё endpoint'ом служил
адрес одного из узлов кластера, и весь этот путь не выполнялся ни разу.

36. Пороги ресурсов кластерного узла применялись к балансировщику: в
    `prod-01` для группы заданы свои, в инвентаре стенда их не было.
    Отдельно стоит запомнить: **порог, равный номинальному размеру ВМ, не
    проходит никогда** — машина «2 ГБ» сообщает 1966 МБ.
37. `api_vip_managed: true` требовал минимум двух LB-узлов, отождествляя
    «управляем балансировщиком» с «поднимаем VIP через keepalived». Без
    keepalived балансировщик один по построению: общего адреса нет.
    Тот же класс, что дефект 21.
38. Пароль VRRP требовался при выключенном keepalived, хотя протокола нет.
    `no_log` на извлечении превратил отсутствующий ключ в отказ без причины.
39. **Проверка выполнялась до применения конфигурации.** Установка пакета
    на реальной машине сразу запускает службу со стоковым конфигом, где
    frontend'а нет; задача «Enable and start» оказывается пустой, наш
    конфиг ложится следом, а перезагрузка висит на handler — тот сработал
    бы только в конце play.

    Контейнерные сценарии пропускали это **структурно**: `policy-rc.d` не
    даёт службам стартовать при установке пакета, поэтому там первый запуск
    шёл уже с готовым конфигом. Сценарий был зелёным на роли, которая на
    живой ВМ не поднимала порт вообще.

    Первое исправление (`flush_handlers`) оказалось неполным: оно лечит
    только первый прогон. Прогон, прерванный между рендером и
    перезагрузкой, оставляет службу со старым конфигом в памяти, а
    повторный запуск ничего не меняет — файл уже правильный. Роль теперь
    сверяется с фактическим состоянием службы.
40. `node_join` зависела от каталога `/etc/kubernetes`, который сама не
    создаёт. До сих пор он всегда оставался от предыдущей установки.

**Наблюдение по `no_log` и `failed_when`.** За этот прогон `no_log`
четырежды скрыл причину отказа, а `failed_when: false` один раз сделал
условие `is failed` вечно ложным — задача восстановления молча не
выполнялась. Одна ошибка мышления: механизм подавления вывода или ошибки
заодно ломает то, что на этот результат опирается. `no_log` оправдан
только там, где секрет действительно попадает в вывод; `ignore_errors`
сохраняет `failed` в результате, `failed_when: false` — нет.

### 5.8. Секрет-бэкенд и Cluster Mesh

41. **Preflight не мог доверять сертификату OpenBao.** Проверка
    доступности выполняется модулем `uri` НА УЗЛЕ, поэтому переменные
    окружения lookup-плагина (`ANSIBLE_HASHI_VAULT_CA_CERT`) на неё не
    действуют — lookup работает на управляющей машине. Параметра для
    своего CA у проверки не было вовсе, и с внутренним OpenBao по HTTPS
    она не прошла бы никогда. Добавлены `openbao_ca_cert` (содержимое PEM)
    и `openbao_ca_cert_path` (путь на узле). `validate_certs` НЕ отключён:
    проверка секрет-бэкенда без проверки сертификата не стоит ничего.

42. **Общий CA затирался чартом.** Способ выпуска сертификатов был
    переведён на `cronJob` только для `clustermesh`, а `hubble` остался на
    умолчании `helm`. При `method: helm` чарт рендерит секрет `cilium-ca` —
    общий центр сертификации всего Cilium — и затирает тот, что роль
    положила из секрет-бэкенда секундой раньше.

    По логам всё выглядело правильно: шаг отработал, секрет создан, порядок
    относительно применения чарта верный. Обнаружено только сравнением
    отпечатков: и наш CA, и сгенерированный чартом называются
    `CN = Cilium CA`, по субъекту неразличимы.

    Правило: **общий CA не выживает, пока хоть один способ выпуска
    остаётся `helm`**.

**Не дефекты проекта, но требуют знания** — расхождения в чарте Cilium
1.19.6, на которые уйдёт время у любого:

* `cilium clustermesh connect` требует Helm-релиза в кластере. При
  `helm template` + `kubectl apply` (раздел 4.3) релиза нет, и штатный путь
  соединения кластеров неприменим.
* `clustermesh.config.enabled` обязан быть `true` даже при пустом списке
  кластеров: Deployment монтирует ConfigMap `clustermesh-remote-users` при
  любом `tls.authMode`, кроме `legacy`, а создаётся он только при
  `config.enabled`. Иначе под уходит в `Init` навсегда.
* `affinity: local` скрывает удалённые backend'ы из `cilium-dbg service
  list`, пока жив локальный. Судить о сборке mesh по этому списку нельзя.

### 5.9. Секрет-бэкенд: роль openbao

45. **Роль отчитывалась об успехе, не настроив хранилище.** Корневой

### 5.10. Роль spire_server

Три ошибки, найденные первым прогоном на живой машине. Все написаны

### 5.11. Cilium mutual authentication

49. **Namespace `cilium-spire` создаётся чартом без меток Pod Security
    Admission.** Под кластерным профилем `baseline` агенты SPIRE не
    стартуют вовсе — им нужен hostPath:

    ```
    pods "spire-agent-..." is forbidden: violates PodSecurity
    ```

    Сервер при этом поднимается, и по статусу Cilium ничего не заметно.
    Лечится метками `privileged` на namespace; их нужно закладывать в
    конфигурацию, а не проставлять руками после каждой установки.

**Результаты проверки механизма** (Cilium 1.19.6, SPIRE из чарта):

| Что | Результат |
| --- | --------- |
| политика пропускает разрешённого | ходит после рукопожатия |
| политика **запрещает** неразрешённого | не проходит — отказной путь проверен |
| оператор регистрирует идентичности | 13 записей, `spiffe://spiffe.cilium/identity/<id>` |
| SPIRE погашен: уже аутентифицированная пара | **работает** |
| SPIRE погашен: новый под с той же идентичностью | **работает** |
| SPIRE погашен: **новая идентичность** | **не проходит** |
| SPIRE погашен, TTL 2 минуты: когда встала работавшая пара | **через 81 секунду** |
| возврат сервера | восстановление само, 46 секунд |

**Срок жизни кеша измерен.** Существующие связи живут не бесконечно: они
держатся, пока действителен сертификат рабочей нагрузки. При выставленном
`default_x509_svid_ttl = "2m"` трафик уже аутентифицированной пары встал
через **81 секунду** после падения сервера — раньше номинального срока,
потому что агент пытается обновить сертификат примерно на половине TTL и,
не сумев, не продлевает аутентификацию.

Отсюда правило: **запас времени определяется сроком жизни сертификата**,
а не наличием кеша. При значении по умолчанию (час) запас — порядка
десятков минут, при двух минутах — полторы минуты.

Это делает TTL ручкой компромисса с прямым эксплуатационным смыслом:
длиннее — дольше переживёте отказ SPIRE, но дольше живёт скомпрометированный
сертификат.

**Возврат сервера** восстанавливает трафик за **46 секунд**, без
вмешательства.

**Вывод для эксплуатации.** Отказ SPIRE не роняет работающее мгновенно, но
и не переживается неограниченно. Порядок событий такой: сразу встают новые
идентичности (выкатка нового сервиса), затем, по мере истечения
сертификатов, отваливается и работавшее. Причина и следствие разнесены во
времени — дежурный увидит сначала «не выкатывается», а потом, вразнобой,
«отваливается работавшее».

Возврат сервера лечит без вмешательства — в отличие от kubelet после
отката etcd (дефект 43).

### 5.12. etcd-backup CronJob

50. **Референсный CronJob не запустился бы никогда.** Команда была написана

    Отказ тихий вдвойне: манифест выглядит правильным, применяется без

### 5.12a. Включение Gateway API

51. **Изменение `cilium-config` кладёт датаплейн на всех узлах, кроме
    одного.** Включение Gateway API добавляет ключи в ConfigMap. Агенты
    перезапускаются сразу: при `rollOutCiliumPods: true` чарт проставляет
    DaemonSet контрольную сумму конфигурации, и `kubectl apply` начинает
    перекат. У Deployment оператора такой отметки нет, пока не задан
    `operator.rollOutPods`, — **шаблон его пода не меняется, и он не
    перезапускается вовсе**. Асимметрия и есть корень дефекта.

    Старый оператор продолжает работать со старой конфигурацией и не
    регистрирует CRD `CiliumEnvoyConfig` и `CiliumClusterwideEnvoyConfig`,
    нужные при включённом Gateway API. Новые агенты ждут их **пять минут**
    и завершаются с `level=fatal: Unable to find all Cilium CRDs necessary
    within 5m0s`.

    Наблюдалось вживую: `ready=1/3`, уцелел ровно тот узел, где под агента
    не перезапускался. Диагностика затруднена тем, что оператор при этом
    `1/1 Running` и в его логе нет ни одной ошибки — он просто не знает,
    что от него чего-то ждут. Совпадение времён: ConfigMap изменён в
    20:55:06, под оператора запущен в 20:52.

    **Почему недостаточно просто задать `operator.rollOutPods`.** Тогда
    оба перекатываются одним `apply`, одновременно, и порядок остаётся
    случайным. Нужен не перезапуск, а очерёдность.

    Исправлено в `cilium_bootstrap/tasks/render_apply.yml` разнесением по
    шагам: ConfigMap рендерится отдельно (`helm template --show-only
    templates/cilium-configmap.yaml`) и применяется **первым**; если его
    данные изменились — перезапускается оператор с ожиданием готовности; и
    только затем применяется остальной манифест. Агенты после этого либо
    перекатываются сами по контрольной сумме, либо, если поколение
    DaemonSet не изменилось, перезапускаются явно — иначе новая
    конфигурация не подействует, ведь агент читает `cilium-config` только
    при старте. Первичная установка под условие не попадает: ConfigMap до
    неё не существует.

    Проверено на живом кластере в обе стороны — включением и выключением
    ключа `debug`. Порядок шагов в выводе соблюдён, агенты перекатились,
    в логе агента появились и затем исчезли 287 строк `level=debug`,
    Gateway продолжал отвечать. Замечание к проверке: поле `Debug` в
    `cilium-dbg config` при этом остаётся `Disabled` — оно про отладку
    датаплейна, другой ключ, и по нему легко сделать неверный вывод.

52. **`GatewayClass` не создаётся никогда.** В чарте Cilium 1.19.6 объект
    закрыт условием

    ```
    or (eq .Values.gatewayAPI.gatewayClass.create "true")
       (and (.Capabilities.APIVersions.Has "gateway.networking.k8s.io/v1/GatewayClass")
            (eq .Values.gatewayAPI.gatewayClass.create "auto"))
    ```

    Умолчание — `auto`, то есть решение отдано проверке возможностей
    кластера. Роль же намеренно вызывает `helm template` **без подключения
    к кластеру** (раздел 4.3: чтобы не появлялся helm release secret),
    поэтому `.Capabilities.APIVersions` пуст и условие ложно всегда.

    Отказ тихий: `enable-gateway-api: "true"` в ConfigMap, контроллер
    `gateway` в операторе запущен, агенты здоровы, `cilium status` без
    замечаний — и при этом `kubectl get gatewayclass` пуст, а любой
    `Gateway` остаётся без реализации. Исправлено явным
    `gatewayAPI.gatewayClass.create: "true"` в values.

    Отдельный урок про проверку: первая попытка доказать зависимость от
    `--api-versions` дала «ноль в обоих случаях» и выглядела опровержением.
    На деле обе команды падали — файла values по указанному пути не
    существовало, а stderr был отправлен в `/dev/null`. Вывод сделан только
    после чтения самого шаблона чарта.

53. **CRD standard-канала недостаточно, `TLSRoute` обязателен.** Он есть
    только в experimental-канале, и в план было записано, что без него
    «Cilium молча отключает поддержку», то есть его можно не ставить. Это
    неверно. Оператор регистрирует тип безусловно, и без CRD контроллер
    `gateway` на каждой реконсиляции от backend-сервиса выдаёт

    ```
    error="no kind is registered for the type v1alpha2.TLSRouteList
           in scheme \"k8s.io/client-go/kubernetes/scheme/register.go:84\""
    ```

    Ошибка идёт из очереди `queue-gw-from-backend-svc`, то есть страдает
    именно пересчёт Gateway при изменении backend'ов. Experimental-канал
    приходится брать, даже если TLS passthrough не используется. План и
    комментарии в values исправлены.

54. **Базовые сетевые политики блокируют трафик, пришедший через
    Gateway.** `default-deny-ingress` из `baseline-policies` отбрасывает
    запросы от Envoy: снаружи это `HTTP 503 upstream connect error ...
    connection timeout`, где про политику нет ни слова и что легко принять
    за неработающее приложение. В Hubble видно однозначно:
    `policy-verdict:none ... Policy denied DROPPED (TCP Flags: SYN)`.

    Источником оказался адрес `10.100.0.230`, который **не принадлежит ни
    одному поду**: это выделенный адрес узла под зарезервированной
    идентичностью `reserved:ingress` (ID 8), под которой Cilium
    представляет свой Envoy. Обычным `NetworkPolicy` такой источник не
    выражается — ни `podSelector`, ни `namespaceSelector` его не выбирают,
    а `ipBlock` потребовал бы перечислять адреса всех узлов. Добавлена
    `CiliumNetworkPolicy` с `fromEntities: [ingress]`; разрешения разных
    типов политик складываются, запрет по умолчанию сохраняется.

    Дефект проявляется только вместе: сами по себе и базовые политики, и
    Gateway API работают.

55. **Запуск синхронизации Argo CD патчем `.operation` молча теряет
    `syncOptions`.** Приём применялся для ручной синхронизации там, где на
    узле нет CLI `argocd`:

    ```
    kubectl -n argocd patch app <name> --type merge \
      -p '{"operation":{"sync":{"revision":"HEAD"}}}'
    ```

    Argo CD **не подставляет** в такую операцию `spec.syncPolicy.syncOptions`
    приложения. Для `cert-manager` это означало потерю `CreateNamespace=true`:
    namespace не создавался, и все 48 задач падали с `namespaces
    "cert-manager" not found`, а среди них — `error running kubectl auth
    reconcile`. Приложение при этом показывало `health=Healthy`, потому что
    здоровых ресурсов у него попросту не было.

    Диагностическая деталь, по которой это ловится: в `syncResult` **нет
    задачи с `Namespace`** — то есть Argo CD её и не планировал. Проверено
    прямым опытом: та же операция с явным
    `"syncOptions":["CreateNamespace=true","ServerSideApply=true"]`
    отрабатывает `Succeeded`, namespace создаётся с нужными метками PSA.

    Процедура в роли `argocd_bootstrap` (`argocd app sync`) верна — CLI
    опции подставляет. Ловушка только у обходного пути через `kubectl`;
    он описан в `docs/VERIFICATION.md` уже с обязательными `syncOptions`.

| вход снаружи | 200 через публичный адрес всех трёх узлов, ответы от разных подов |
| TLS | 200 с проверкой цепочки до CA cert-manager; issuer `CN = stand-ca` |
| отказ TLS без доверия к CA | `exit=60` |
| отказ TLS с чужим именем в SNI | `exit=35` |

**Ограничение стенда.** Адрес выдан из пула `192.0.2.0/29` (RFC 5737,
диапазон для документации) — намеренно, чтобы исключить конфликт с
адресацией облака. Он **доступен только изнутри**: запрос с узла на
`192.0.2.0` доходит (`cilium-dbg service list` показывает запись
`LoadBalancer`), а снаружи — нет, потому что анонсировать адрес некому.
Для этого нужны L2-анонсы или BGP, и ни то, ни другое в облачной VPC не
работает. Проверка входа снаружи выполнена через NodePort. На физической
площадке эта позиция требует отдельной проверки с L2 или BGP.

**Отдельный урок про методику.** Первая проверка HTTPS снаружи дала
`HTTP 000` со всех трёх узлов и выглядела как отказ шлюза. На деле curl
на управляющей машине уходил в локальный прокси `127.0.0.1:1081`,
который игнорирует `--resolve`. С `--noproxy '*'` — 200 отовсюду.
Отсюда правило: проверка снаружи выполняется в обход прокси, иначе
проверяется прокси, а не кластер.

### 5.13. Продление PKI при включённых mesh и mutual authentication

Проверен риск, записанный в план: перевыпуск сертификатов control plane
**не затрагивает** общий центр сертификации Cilium и центр SPIRE —
отпечатки обоих до и после совпали, изменился только сертификат apiserver.
Mutual authentication продолжил работать, включая отказной путь.

### 5.14. Отказные пути

Первые отказные прогоны за проект. До них всё проверялось только по
счастливому пути.

**Потеря control-plane.** На одном кластере погашен apiserver. Нагрузка
продолжила работать, а соседний кластер всё время получал ответы от его
подов через глобальный сервис: 4 из 8 запросов. То есть отказ управляющего
слоя одной площадки **не прерывает межкластерный трафик** — данные ходят
по датаплейну, а `clustermesh-apiserver` соседа продолжает отдавать
известное ему состояние.

**Проверки preflight.** Восемь проверок выполнены на заведомо неверных
данных, все восемь сработали с внятным сообщением: DNS вне service CIDR,
совпадение pod и service CIDR, адрес узла внутри pod CIDR, неизвестный
секрет-бэкенд, неизвестный провайдер шифрования, неподдерживаемый
дистрибутив, старое ядро, несовпадение MTU.

Непроверенным осталось требование нечётного числа control-plane узлов: на
стенде в кластере один узел, а для проверки нужно два.

**Замечание о методике, стоившее двух ложных выводов.** При `loop` Ansible
печатает `failed:` на каждый элемент, а не `fatal:`. Детектор, ищущий
только `fatal`, объявляет сработавшие проверки несработавшими. Ошибка
ровно того класса, ради поиска которого отказные пути и затеваются, —
только неисправным оказался сам тест.

### 5.15. Разрыв связи между площадками

Не дефекты кода, но свойства, которые нужно знать при эксплуатации
мультикластера. Найдены первым отказным прогоном.

* **Статус mesh не отражает разрыв.** `cilium-dbg status --all-clusters`
  всё время разрыва показывает `1/1 remote clusters ready` и
  `0 reconnections`. При KVStoreMesh агенты подключаются к ClusterIP
  локального `clustermesh-apiserver`, поэтому статус отражает состояние
  локального кеша, а не связь с площадкой. Разрыв виден только в логах
  контейнера `kvstoremesh`.

  Оповещение о потере связи между ДЦ на этом статусе строить нельзя.

* **Трафик уходит на исчезнувшие backend.** Погашенный на соседней
  площадке под глобального сервиса продолжал считаться активным: из
  восьми запросов два завершились отказом. Деградация частичная, а не
  переключение на локальные backend целиком. Лечится
  `service.cilium.io/affinity: local`.

### 5.16. Восстановление etcd на кластере в составе mesh

43. **kubelet не перезапускался после отката, и раскатка агентов вставала
    намертво.** Дефект 35 добавил перезапуск kube-proxy и CNI, но kubelet
    остался. После отката он перестаёт обрабатывать удаление подов: под
    получает `deletionTimestamp` и висит в `Terminating` бесконечно, причём
    **событий у пода нет вовсе**. Раскатка `DaemonSet` упирается в
    «0 out of 3 new pods have been updated» и не двигается.

    Playbook перестроен: kubelet перезапускается на ВСЕХ узлах отдельным
    play и строго ДО перезапуска агентов. Пока kubelet не перезапущен,
    перезапускать `DaemonSet` бессмысленно — их поды не будут ни удалены,
    ни созданы.

44. **`ansible_date_time` при включённом кешировании фактов — не текущее
    время.** В `ansible.cfg` задано `fact_caching = jsonfile` со сроком
    час, поэтому метка времени берётся из ПЕРВОГО сбора фактов. Два
    запуска в пределах часа дают одинаковый суффикс.

    Затронуты четыре места, и два из них хуже третьего, потому что
    молчат:

    | Где | Последствие |
    | --- | ----------- |
    | `etcd_backup/snapshot_once.yml` | второй снимок молча затирает первый |
    | `renew-control-plane-certs.yml` (×2) | резервная копия PKI перезаписывается, теряется состояние до продления |
    | `restore-etcd.yml` | падает посреди восстановления, уже остановив control plane |

    Везде заменено на `now(utc=true, ...)`: оно вычисляется при рендере
    шаблона и кешированием не затрагивается.

**Результат прогона.** Кластер откачен к состоянию снимка, метка исчезла,
узлы `Ready`, ни одного пода вне `Running`, `DaemonSet` Cilium раскатан
полностью. **Cluster Mesh уцелел**: соседний кластер виден, синхронизация
идёт. Доступ к API проверен изнутри пода. Прежние каталоги данных
сохранены с различающимися метками времени.

### 5.17. Восстановление etcd

35. **После отката поды теряют доступ к apiserver, а кластер при этом
    выглядит здоровым.** Восстановление откатывает resourceVersion назад,
    watch-подписки агентов на узлах рвутся, и состояние, выведенное из них,
    остаётся прежним: kube-proxy решил, что у сервиса `kubernetes` нет
    endpoint'ов, и записал `-j REJECT` с комментарием `has no endpoints`;
    у Cilium запись того же сервиса в BPF осталась с пустым списком backend.
    Само это не чинится — наблюдалось 25 минут.

    Диагностика была обманчива вдвойне. Узлы `Ready`, поды `Running`,
    `kubectl` с узла работает — потому что ходит на адрес узла напрямую,
    минуя ClusterIP. DNS через ClusterIP тоже работал: у CoreDNS backend'ы
    сохранились, пустым оказался только `kubernetes`. Argo CD при этом
    видел изменения в Git, но не мог записать результат.

    Playbook теперь перезапускает агенты, чьё состояние выведено из
    watch-подписок, и проверяет, что у сервиса `kubernetes` столько
    endpoint'ов, сколько control-plane узлов. Исправление проверено
    повторным восстановлением: доступ из пода есть сразу, Argo CD
    реконсилирует без вмешательства.

    **Следствие для методики проверки:** доступ к API после восстановления
    проверяется ИЗНУТРИ ПОДА. Проверка с хоста этот класс отказов не видит.
