## 2. Стенд

Проверялось на Yandex Cloud: пять ВМ, Ubuntu 24.04, 4 vCPU / 3.9 ГБ /

**Отличия стенда от production**, влияющие на полноту проверки:

Последняя проверка написана после того, как `: ` внутри незакавыченного

ни syntax-check этот класс ошибок не ловят.

### 3.2. Контейнерные сценарии

Удалены из проекта. Они находили дефекты (девять, раздел 5.1), но покрывали
то же, что и стенд из ВМ, а поддержка второго стенда обходилась дороже
пользы. С ними ушли два вида покрытия, которых у стенда нет: роль
`haproxy_keepalived`, непроверяемая в облаке из-за VIP на L2, и отказные
пути `preflight`, где сценарии подсовывали заведомо неверные значения.

### 3.3. Установка с нуля

`site.yml` целиком, одной командой, на пяти чистых ВМ:

```
k8s-cp-01      ok=271  changed=70   failed=0
k8s-cp-02      ok=132  changed=47   failed=0
k8s-cp-03      ok=132  changed=47   failed=0
k8s-worker-01  ok=121  changed=42   failed=0
```

Подтверждено на живом кластере: узлы `Ready`, три здоровых члена etcd,
Cilium 4/4, шифрование `k8s:enc:secretbox:v1:key1`, аппрув serving-CSR,
audit log пишется, флаги безопасности в манифесте apiserver.

### 3.4. Обслуживание

| Сценарий | Результат |
| -------- | --------- |
| `add-node` | узел присоединён и `Ready`, Cilium подхватил, кворум etcd не затронут |
| `remove-node` | узел выведен, kubelet остановлен, под-сирота собран мусорщиком |
| `renew-control-plane-certs` | продлено на трёх узлах; **проверен и отказной путь** — при искусственном таймауте манифесты возвращаются, кластер цел |
| `upgrade/*` | 1.34.10 → 1.35.7 на пяти узлах, приложение пережило раскат |
| `rotate-etcd-encryption-key` | все четыре фазы; см. ниже |
| `80-backup.yml` | таймер включён на трёх узлах, дождались фактических срабатываний |
| `restore-etcd.yml` | откат кластера к состоянию снимка; см. ниже |

Обновление выполнено по процедуре раздела 27: сверена матрица
совместимости, CNI обновлён отдельно через GitOps (Cilium 1.19.6
заявляет только 1.31–1.34, поэтому потребовался переход на 1.20).
Шлюз `compatibility_matrix_verified` проверен: без подтверждения
обновление не стартует.

Ротация ключа шифрования etcd прослежена по префиксу записи в etcd на
каждой фазе:

| Фаза | Конфиг apiserver | Префикс в etcd |
| ---- | ---------------- | -------------- |
| до | `key1` | `key1` |
| 1 | `key1, key2` | `key1` — пишем старым, читаем обоими |
| 2 | `key2, key1` | `key1` — пишем новым |
| 3 | `key2, key1` | `key2` — все 12 объектов перешифрованы |
| 4 | `key2` | `key2` |

Секрет, записанный до ротации, читается после её завершения.

Восстановление проверялось так, чтобы отличить настоящий откат от
видимости работы: после снятия снимка создавались объекты, которых в нём
заведомо нет, и проверялось их исчезновение.

| Объект, созданный после снимка | После восстановления |
| ------------------------------ | -------------------- |
| `ns/after-snapshot` | `NotFound` |
| `cm/restore-canary` | `NotFound` |
| `secret/secret-canary` | `NotFound` |
| `podinfo` увеличен до 4 реплик | вернулся к 2 — значению из снимка |

Состояние на момент снимка уцелело полностью: семь namespace, 11 секретов,
Argo CD Application, рабочие нагрузки. Зашифрованный Secret читается —
ключ и его имя совпали с теми, которыми снимок записан. После
восстановления кластер принимает запись, новые Secrets шифруются.

Три члена etcd стартовали как новый кластер и здоровы; все четыре узла
`Ready`, посторонних подов нет. Прежний каталог данных сохранён на каждом
узле как `member.pre-restore-*`.

Восстановление одного члена из снимка невозможно: два остальных сохранят
прежнюю историю и отвергнут его. Поэтому снимок разворачивается на всех
узлах разом, а `serial` в этом playbook недопустим — нужен барьер, который
даёт линейная стратегия.

Резервное копирование проверялось с временно укороченным интервалом:
таймер сработал многократно, снимки прошли `etcdutl snapshot status`
(877 ключей, ревизия 8303). `RandomizedDelaySec` разводит узлы по времени,
одновременных снимков нет. После проверки расписание возвращено к штатному.

**Замечание, не дефект:** снимок пишется в каталог данных etcd и только
затем переносится в каталог резервных копий — иначе файл не вынести из
контейнера, туда смонтирован hostPath. На стенде каталоги на одном разделе;
при отдельном диске под etcd (раздел 5.2) снимок временно занимает место
на самом критичном томе. Стоит следить за свободным местом.

### 3.5. GitOps

- root Application применяется из репозитория, без finalizer и без `automated`
- takeover Cilium: `kubectl diff` показал **ноль различий** в spec,
  `OutOfSync` вызван только tracking-метаданными Argo CD
- пользовательское приложение (podinfo) развёрнуто через Git, PSA
  `restricted` подтверждён отклонением привилегированного Pod
- обновление Cilium через PR в отдельной ветке

## 4. Что осталось проверить

### 4.1. Первоочередное

| Сценарий | Почему важно | Что нужно |
| -------- | ------------ | --------- |
| **Роль `haproxy_keepalived`** | единственная роль без какого-либо покрытия | bare-metal или сеть с поддержкой VRRP |
| **Отказные пути `preflight`** | прогоны идут по счастливому пути | подстановка заведомо неверных значений вручную |

### 4.2. Требует написания

| Что | Состояние |
| --- | --------- |
| Проверка продления **истёкших** сертификатов | сценарий сложнее: apiserver не принимает соединения, `kubeadm` не читает конфигурацию из кластера |

### 4.3. Не проверить на текущем стенде

| Что | Препятствие |
| --- | ----------- |
| `05-load-balancer.yml` вживую | в облаке не поднять произвольный VIP на L2; нужен bare-metal или сеть с поддержкой VRRP |
| Отдельный диск под etcd | ВМ стенда с одним диском |
| Работа через Harbor и внутренние зеркала | нужен закрытый контур |
| OpenBao как секрет-бэкенд | нужен OpenBao |
| Приватный GitOps-репозиторий с deploy key | код есть, путь SSH не проверялся |
| `firewall_manage: true` (ufw) | не включался; риск конфликта с Cilium не проверен |
| Роль `haproxy_keepalived` | покрытия не осталось: контейнерные сценарии удалены |

### 4.4. Из обязательного списка компонентов (раздел 21.1)

Не установлено и не проверено ничего из wave -10 и выше, кроме Cilium
и Argo CD: kubelet-csr-approver, cert-manager, External Secrets Operator,
CSI и StorageClass, ingress или Gateway API, metrics-server,
observability-агенты, policy engine, etcd-backup CronJob, базовые
NetworkPolicy, ResourceQuota, LimitRange, PodDisruptionBudget,
PriorityClass.

Следствие: проверка storage в `cluster_validation` остаётся отключённой,
а serving-сертификаты kubelet аппрувятся вручную.

## 5. Дефекты, найденные прогонами

Сгруппированы по тому, чем именно обнаружены. Ни один не виден линтерам.

### 5.1. Контейнерные сценарии (удалены из проекта)

1. `provisioner.inventory.links` полностью отключает inline `host_vars`
   и `group_vars` — все 14 сценариев работали без своих переменных.
2. `ANSIBLE_ROLES_PATH` не задавался — роль не находилась по имени.
3. `privileged: false` (из примера в документе) — systemd в контейнере
   не стартует вообще.
4. `chronyd -Q` как валидатор конфига не проверяет синтаксис, а опрашивает
   NTP-серверы и ждёт: при недоступном NTP `os_prepare` висел бесконечно.
5. Каталог `/etc/systemd/journald.conf.d` не создавался перед записью.
6. `logrotate` настраивался, но не устанавливался.
7. `| first` по пустой последовательности ронял задачу на рендере
   `fail_msg`, пряча настоящую причину.
8. `groups['all']` включает `localhost` провижнера без `node_ip`.
9. `: ` внутри незакавыченного условия `assert` делает его отображением.

### 5.2. Первый прогон на ВМ

10. `validate:` модуля `template` неприменим к chronyd на Ubuntu:
    AppArmor запрещает читать временный файл даже под root.
11. `trim_blocks` съедает перевод строки после Jinja-комментария —
    отступ склеивается со следующей строкой, YAML ломается.
12. Проверка ключа шифрования через `| b64decode | length` отвергала
    **валидные** ключи: фильтр возвращает текст, и случайные байты дают
    неверную длину.
13. Роль `containerd` проверяла себя через `crictl`, который приезжает
    на следующем этапе.
14. `python3-kubernetes` нигде не устанавливался, хотя модули
    `kubernetes.core` выполняются на control-plane узле.
15. Межролевые ссылки на переменные: defaults одной роли не видны другой.
16. `\\s` в свёрнутом скаляре YAML остаётся двумя символами.
17. Рассогласование labels между шаблоном join и проверкой.
18. `no_log` на проверках формата скрывал причину отказа.

### 5.3. Конфигурации, которые роли не допускали

19. Порочный круг с hostname: preflight требовал того, что исправляет
    `os_prepare` на следующем этапе.
20. `gitops.repo_url` требовался на этапе 00, хотя нужен этапам 50 и 60 —
    запрещало поэтапное развёртывание.
21. `api_vip_managed: false` смешивал два разных случая: внешний LB и
    endpoint на самом узле кластера.
22. Деплой-ключ требовался безусловно — публичный репозиторий по HTTPS
    не поддерживался.

### 5.4. Валидация

23. Проверка шифрования затягивала в переменную двоичное значение из etcd.
24. Путь тестового образа собирался как `registry_host + /k8s/` — верно
    только для зеркала в Harbor.

### 5.5. Обслуживание

25. `add-node` использовал `--limit`, что ломало межузловые проверки
    preflight: факты остальных узлов не собирались.
26. `remove-node` удалял объект Node до `kubeadm reset` — kubelet мог
    перерегистрировать узел.
27. Возврат манифестов не был в `always`: при таймауте play прерывался
    с манифестами вне каталога.
28. **Секция `always` не выполняется, когда файл включается из handler.**
    Воспроизведено дважды: control plane оставался лежать. Тот же файл,
    включённый обычной задачей, отрабатывает целиком.

### 5.6. Ротация ключа шифрования и резервное копирование

Найдены вторым полным прогоном на чистых ВМ.

31. **Ротация не стартовала ни при каком состоянии ключа**, если бэкенд
    не OpenBao. `fail_msg` безусловно ссылался на `openbao_cluster_path`,
    а Ansible вычисляет аргументы задачи ДО проверки условий: при
    `secret_backend: vault_file` переменная не определена, и assert падал,
    даже когда ключ корректен. `no_log` на этой задаче прятал причину.
32. **`run_once` при `serial` выполняется раз на ПАРТИЮ, а не раз на play.**
    При `serial: 1` каждый узел — своя партия, поэтому перешифровка всех
    Secrets запускалась на каждом control-plane узле. Помимо лишней работы
    это гонка: параллельные `kubectl replace` дают конфликт
    `resourceVersion`, а `any_errors_fatal` обрывает ротацию посередине.
33. **Финальная инструкция самого playbook приводила к потере доступа ко
    всем Secrets.** Имя ключа было зашито константой `key1`, а ротация
    оставляет данные под именем `key2`. Выполнение инструкции «повысить
    ключ в бэкенде» приводило к тому, что следующий штатный прогон
    `40-control-plane-init.yml` отдавал apiserver верный ключ под чужим
    именем. Проверено изолированно на одном узле, ответ apiserver:
    `no matching key was found for the provided Secretbox transformer`.
    Имя ключа теперь хранится в секрет-бэкенде рядом с самим ключом,
    ротация чередует `key1 ⇄ key2` (жёсткий переход ломался бы уже на
    второй ротации), инструкция фазы 4 требует обновить оба поля.
34. **`80-backup.yml` падал на всех узлах, кроме первого**: роль писала
    референсный манифест CronJob в `/etc/kubernetes/bootstrap`, а этот
    каталог создают bootstrap-роли, выполняемые только на первом
    control-plane узле. systemd timer на остальных узлах не настраивался.

### 5.7. Обновление

29. Playbook не переключал apt-репозиторий на целевую minor-версию:
    `pkgs.k8s.io` держит отдельный репозиторий на каждую ветку.
30. Валидация после обновления сверялась с `kubernetes_version` из
    inventory, который оператор ещё не успел поправить.

## 6. Прогоны на чистых ВМ

Выполнено два полных прогона с нуля на новых ВМ. Второй прошёл по плану:

1. `00-stand-prerequisites.yml` — hostname и `/etc/hosts` (в production это
   обеспечивают DNS и golden image).
2. `site.yml` целиком — ноль отказов, счётчики задач совпали с первым
   прогоном до единицы (271 / 132 / 132 / 121).
3. `rotate-etcd-encryption-key.yml` — четыре фазы с проверкой префикса
   в etcd между каждой.
4. `80-backup.yml` — таймер, с ожиданием фактического срабатывания.
5. `add-node.yml` — пятая ВМ введена, Cilium 5/5, кворум не затронут.
6. GitOps: root Application синхронизирован вручную (`automated` намеренно
   выключен), развернулись дочерние Application и podinfo на двух worker.
7. `remove-node.yml` — узел выведен, реплики переехали, под-сирота Cilium
   собран мусорщиком (`desired` вернулся к 4).
8. `renew-control-plane-certs.yml` — продлено на трёх узлах, застрявших
   манифестов нет.
9. `restore-etcd.yml` — написан по разделу 28.4 и проверен: кластер
   откачен к состоянию снимка.

Не прогонялось на этом стенде: `05-load-balancer.yml` (в облаке не поднять
произвольный VIP) и серия `upgrade/*` — она проверена на предыдущем стенде
и требует ветки `cilium-1.20`, поскольку Cilium 1.19.6 заявляет поддержку
только Kubernetes 1.31–1.34.
