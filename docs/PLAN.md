Что делать дальше, в каком порядке и почему именно в таком. Состояние
проверенного — в `TEST-PLAN.md`, решения по спорным развилкам — в `adr/`.

## 0. Восстановление стенда

**ВМ погашены.** Локальные файлы `inventories/yc-test/hosts.local.yml`,
`group_vars/all/99-local.yml` и `secrets.vault.yml` содержат адреса
несуществующих машин — их нужно переписать под новые.

Требуется **шесть** ВМ, Ubuntu 24.04, в одной подсети:

| Роль | Количество | Ресурсы |
| ---- | ---------- | ------- |
| control-plane | 3 | 4 vCPU / 4 ГБ / 20 ГБ |
| worker | 2 | 4 vCPU / 4 ГБ / 20 ГБ |
| балансировщик | 1 | 2 vCPU / 2 ГБ / 20 ГБ |

Порядок подъёма:

1. Адреса в `hosts.local.yml`; приватный адрес балансировщика — в
   `group_vars/all/99-local.yml` как `api_vip`.
2. Новый ключ шифрования в `secrets.vault.yml`:
   `head -c 32 /dev/urandom | base64`. Пароль VRRP не нужен, пока
   `keepalived_enabled: false`.
3. `inventories/yc-test/00-stand-prerequisites.yml` — hostname и `/etc/hosts`.
4. `playbooks/site.yml` целиком.
5. Синхронизация Argo CD: root Application, затем дочерние.
   **Через `argocd app sync`, а не `kubectl patch`**: сырой патч поля
   `operation` не наследует `syncOptions` из `spec`, и `CreateNamespace`
   не срабатывает.

Повторная установка на тех же ВМ — сначала
`inventories/yc-test/99-stand-teardown.yml`.

## 1. Дешёвое и ни от чего не зависящее

Делается на текущем стенде, внешних условий не требует.

### 1.1. Шифрование трафика WireGuard

Одно значение в values Cilium. Закрывает частое требование «трафик
шифруется в транзите» **без** service mesh, без ADR по нему и без второго
кластера.

Проверка: снять трафик между узлами и убедиться, что он не читается;
`cilium-dbg status` показывает включённое шифрование.

### 1.2. Базовые политики через GitOps

`ResourceQuota`, `LimitRange`, базовые `NetworkPolicy`,
`PodDisruptionBudget`. Чистые манифесты, внешних зависимостей нет.

PDB имеет смысл только теперь, когда worker-узлов два: при одной реплике
`minAvailable: 1` блокирует вытеснение и ломает вывод узла.

### 1.3. etcd-backup CronJob

Документ (раздел 28.1) считает основным механизмом именно CronJob, а
systemd timer — запасным для контуров, где запрещён hostPath. Проверен пока
только запасной. Референсный манифест роль `etcd_backup` уже рендерит в
`/etc/kubernetes/bootstrap/`.

## 2. Регламент на топологии с балансировщиком

Все эти сценарии проверялись, когда endpoint'ом служил адрес узла кластера.
С HAProxy между узлами условия другие.

| Сценарий | Что проверяет именно теперь | Приоритет |
| -------- | --------------------------- | --------- |
| `renew-control-plane-certs` | попадёт ли адрес LB в **перевыпущенные** сертификаты | высокий |
| `add-node` / `remove-node` | появится ли узел в backend'ах HAProxy и уберётся ли выведенный | средний |
| `restore-etcd` | достаточно ли перезапуска kube-proxy и CNI | средний |
| `upgrade/*` | переживёт ли балансировщик поочерёдный перезапуск apiserver | средний |

Продление PKI — первое по важности: `kubeadm certs renew` берёт SAN из
конфигурации кластера, и если `controlPlaneEndpoint` там прописан, всё
сойдётся. Это предположение, а не проверенный факт; ошибка здесь тихо
ломает кластер через год.

## 3. Отказные пути

Все прогоны до сих пор шли по счастливому пути.

| Что | Как |
| --- | --- |
| Проверки `preflight` | подставить заведомо неверные значения и убедиться, что каждая срабатывает |
| Потеря control-plane узла | погасить один; кластер должен жить, HAProxy — увести трафик |
| Потеря балансировщика | погасить; проверить предсказание, что control-plane продолжит работать, а worker-узлы отвалятся |

Последние два дают больше уверенности, чем несколько зелёных прогонов
установки, и стоят минут.

## 4. Мультикластер

**ADR пишется до реализации**, потому что ключевые решения принимаются на
этапе планирования адресов: развести PodCIDR после установки кластера
нельзя.

### 4.1. ADR 0002 — мультикластерная связность

Разобрать:

* **Схема адресации.** Сейчас `pod_network_cidr: 10.100.0.0/16` задан в
  `group_vars`; склонированный inventory даст совпадение, и Cluster Mesh не
  соберётся. Нужна схема, выделяющая диапазон на кластер.
* **Где живут секреты пары кластеров.** Обмен CA и endpoint партнёра —
  секреты, специфичные для пары. В публичный Git они не пойдут. Это
  упирается в секрет-бэкенд, то есть в OpenBao и External Secrets Operator,
  которых нет.
* **Нужен ли mesh вообще** или достаточно связности. Cluster Mesh даёт
  обнаружение сервисов между кластерами; идентичность и L7-политики — это
  отдельно и Cluster Mesh не требует.

  При этом стоит учесть GAMMA (ADR 0001, раздел 1.1): с версии 1.1.0
  Gateway API покрывает и east-west трафик, привязывая маршруты напрямую к
  Service. Выбор реализации Gateway API оказывается частично и выбором
  mesh, поэтому решения по разделам 4 и по Gateway API лучше принимать
  вместе, а не по очереди.
* **Cilium mutual authentication против Istio.** У Cilium это beta в 1.19,
  рукопожатие вынесено за пределы соединения, конфиденциальность
  обеспечивает WireGuard или IPsec, а не TLS на соединение. Istio даёт
  классический mTLS ценой второго data plane. Linkerd — компромисс.

### 4.2. Подготовка проекта

* переменная `cluster_id` (1–255), сейчас её нет;
* `cluster.name` и `cluster.id` в values Cilium;
* разведение `pod_network_cidr` и `service_network_cidr` по инвентарям.

### 4.3. Второй кластер и Cluster Mesh

Ещё 4–5 ВМ. **В той же подсети** — тогда связность узлов по InternalIP
появляется сама, и это самый дешёвый способ проверить механизм.

Затем `clustermesh-apiserver` в каждом кластере и обмен секретами.
Проверка: `cilium-dbg status --all-clusters`, глобальный сервис,
доступный из обоих кластеров.

## 5. Заблокировано внешними условиями

| Что | Чем заблокировано |
| --- | ----------------- |
| Keepalived и общий VIP | нужна сеть с поддержкой VRRP; в облаке L2-VIP не поднять |
| Gateway API | ADR 0001: требует замены kube-proxy, а та — отказоустойчивого endpoint. Учесть GAMMA: выбор реализации затрагивает и east-west |
| External Secrets Operator | нужен OpenBao |
| Приватный GitOps по SSH | нужен deploy key и приватный репозиторий |
| Работа через Harbor и внутренние зеркала | нужен закрытый контур |
| Отдельный диск под etcd | нужна ВМ с дополнительным томом |
| `firewall_manage: true` | не включался; риск конфликта с Cilium не проверен |
| Продление **истёкших** сертификатов | сценарий требует отдельной подготовки: apiserver не принимает соединения, `kubeadm` не читает конфигурацию из кластера |

## Порядок

1. Поднять стенд (раздел 0).
2. WireGuard — дёшево и независимо (1.1).
3. Продление PKI на новой топологии (2) — единственное, что может тихо

4. Отказные пути (3) — минуты, а уверенности больше, чем от повторных
   установок.
5. Базовые политики и etcd-backup CronJob (1.2, 1.3).
6. ADR 0002 (4.1), затем подготовка проекта (4.2).
7. Второй кластер (4.3) — когда решено, где живут секреты пары.
