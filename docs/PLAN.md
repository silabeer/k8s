## 0. Воспроизведение стенда с нуля

Требуется **восемь** ВМ, Ubuntu 24.04: по три на кластер в двух разных
подсетях, одна под секрет-бэкенд и одна под реестр артефактов.

| Роль | Кол-во | Ресурсы |
| ---- | ------ | ------- |
| control-plane | 1 на кластер | 4 vCPU / 4 ГБ / 20 ГБ |
| worker | 2 на кластер | 4 vCPU / 4 ГБ / 20 ГБ |
| OpenBao | 1 | 2 vCPU / 2 ГБ / 20 ГБ |
| Реестр артефактов | 1 | 4 vCPU / **8 ГБ** / **50 ГБ** |

Требования к реестру выше не случайно и проверены на практике. 4 ГБ не
хватает: стек поднимает OpenSearch, PostgreSQL, backend, web и два
сканера, и при первой же загрузке слоя по 300–600 МБ с одновременной
индексацией приходит OOM-killer. Диск — это кеш на весь кластер: только
образы Cilium, Argo CD, cert-manager, etcd и kube-компонентов дают
7–8 ГБ, плюс зеркало пакетов ОС.

Сети: подсети кластеров должны видеть друг друга; между узлами разных
кластеров нужны **UDP 51871** (WireGuard) и **TCP 32379** (NodePort
`clustermesh-apiserver`). ВМ с OpenBao должна быть доступна **с
управляющей машины** по 8200: lookup выполняется там, а не на узлах.

### 0.1. Что автоматизировано

* установка кластеров — `site.yml`;
* реестр артефактов и его репозитории — роль `artifact_keeper`,
  playbook `92-artifact-keeper.yml`; проверено на живом сервере,
  идемпотентно;
* раскладка общего CA из секрет-бэкенда — роль `cilium_bootstrap`;
* подготовка стенда — `00-stand-prerequisites.yml`;
* разбор стенда — `99-stand-teardown.yml`.

### 0.2. Что делается руками — и это разрыв

Ниже перечислено то, для чего роли **не написаны**. Пока эти шаги
выполняются вручную, «воспроизвести с нуля одной командой» не получится.

1. ~~Развёртывание OpenBao.~~ **Автоматизировано:** роль `openbao`,
   playbook `91-openbao.yml`. На живом сервере роль не выполнялась, но
   процедура, которую она кодирует, проверена вручную целиком.
2. **Генерация общего CA** для Cluster Mesh и запись его в бэкенд вместе
   с ключами шифрования etcd каждого кластера по путям
   `kv/kubernetes/<cluster_name>`. Ролью не покрыто.
3. **Локальные файлы инвентаря** — `hosts.local.yml`,
   `group_vars/all/99-local.yml` с адресами, `openbao_ca_cert`. В git не
   попадают намеренно.
4. **Адреса соседнего кластера** в `clustermesh.config.clusters` values
   Cilium — их знает только тот, кто поднял ВМ.
5. **Переменные окружения** управляющей машины:
   `ANSIBLE_HASHI_VAULT_TOKEN` и `ANSIBLE_HASHI_VAULT_CA_CERT`. Роли
   вызывают lookup только с `url`, поэтому иначе первый же прогон падает

**Что осталось автоматизировать** — пункт 2: playbook начальной загрузки
секретов, который генерирует общий CA и раскладывает ключи шифрования по
путям кластеров. После него воспроизведение сведётся к «поднять ВМ,
вписать адреса, запустить playbook по порядку».

### 0.3. Порядок

1. Поднять семь ВМ, проверить связность между подсетями и доступность
   8200 с управляющей машины.
2. Развернуть OpenBao (`91-openbao.yml`), сгенерировать общий CA и
   разложить секреты — второе пока вручную.
2a. Развернуть реестр (`92-artifact-keeper.yml`) и дождаться, пока он
   наполнится: он единственный в контуре ходит в интернет, остальные — нет.
   Корневой сертификат Caddy забрать с него и вписать в `registry_ca_cert`
   инвентарей кластеров вместе с `registry_mirrors` и адресами артефактов.
3. Заполнить локальные файлы инвентарей обоих кластеров.
4. `00-stand-prerequisites.yml` для каждого кластера.
5. `site.yml` для каждого кластера.
6. Вписать адреса соседа в values Cilium обоих кластеров, применить
   `50-cni-bootstrap.yml`.
7. Проверить mesh: `cilium-dbg status --all-clusters` и переезд
   глобального сервиса между кластерами.

**Важно:** OpenBao после перезапуска своей ВМ запечатывается и требует два
ключа из трёх. Без него не проходит preflight обоих кластеров. Ключи
распечатывания и корневой токен хранятся у оператора.

## 1. Дешёвое и ни от чего не зависящее

Делается на текущем стенде, внешних условий не требует.

### 1.1. Шифрование трафика WireGuard — выполнено

Включено на обоих кластерах и проверено дампом: при обмене между подами
разных узлов на физическом интерфейсе видно только UDP 51871, пакетов
открытого VXLAN на 8472 — ноль.

Знать при чтении статуса: control-plane узлы показывают
`NodeEncryption: OptedOut` — это штатное исключение по метке
`node-role.kubernetes.io/control-plane`, трафик между подами на них
шифруется всё равно (ADR 0002, раздел 3.2).

### 1.2. Базовые политики через GitOps — почти выполнено

Развёрнуты и проверены: `ResourceQuota`, `LimitRange`, `NetworkPolicy`
(запрет по умолчанию плюс разрешения), а также `CiliumNetworkPolicy` для
трафика от Gateway API (дефект 54).

**Остался `PodDisruptionBudget`.** Он имеет смысл только теперь, когда
worker-узлов два: при одной реплике `minAvailable: 1` блокирует
вытеснение и ломает вывод узла. Проверять обязательно в обе стороны —
что при двух репликах drain проходит, а при одной блокируется, — иначе
проверен не PDB, а его отсутствие.

### 1.3. External Secrets Operator

Закрывает цепочку раздела 22 документа: OpenBao → ESO → Secret в
кластере. Сейчас секреты попадают в кластер только через Ansible на этапе
установки; ESO нужен для тех, что меняются в течение жизни кластера.

**Требует живого OpenBao**, а его ВМ погашена. Поднимать заново стоит
ролью `openbao` (`91-openbao.yml`) — она до сих пор ни разу не
выполнялась на настоящем сервере, и этот прогон закрыл бы сразу две
позиции.

### 1.4. etcd-backup CronJob — выполнено

Проверен: задание отрабатывает, снимок целостен. По дороге найден дефект
50 — манифест был написан на `/bin/sh`, которого в образе etcd нет.

## 2. Регламент на текущей топологии

Сценарии проверялись на одиночном кластере без Cluster Mesh и, отдельно,
на топологии с выделенным балансировщиком. Ни один не выполнялся на
кластере, состоящем в mesh, — а там условия другие.

| Сценарий | Что проверяет именно теперь | Приоритет |
| -------- | --------------------------- | --------- |
| `restore-etcd` | ✅ пройдено: mesh уцелел, найдены дефекты 43 и 44 | — |
| `renew-control-plane-certs` | ✅ пройдено: общие CA не затронуты, mutual auth уцелел | — |
| `add-node` / `remove-node` | подхватит ли соседний кластер изменение состава узлов | средний |
| `upgrade/*` | переживёт ли mesh поочерёдный перезапуск apiserver | средний |

`restore-etcd` — первое по важности. Дефект 35 показал, что после отката
агенты на узлах остаются с состоянием «до», и понадобился их перезапуск.
В кластере, состоящем в mesh, состояние сложнее: добавляются
`clustermesh-apiserver` и связь с соседом. Проверять доступ **изнутри
пода**, а не с узла.

Продление PKI опасно отдельно: перевыпуск не должен затрагивать общий
`cilium-ca`. Если затронет — соседний кластер перестанет доверять, а
обнаружится это не сразу.

## 4. Мультикластер и шифрование — выполнено

Развёрнуто и проверено: два кластера, Cluster Mesh собран, глобальный
сервис переезжает между площадками при потере локальных подов. Подробности
и результаты — в ADR 0002, раздел 8.

Осталось из этого направления: проверить `restore-etcd` на кластере,
состоящем в mesh (могут понадобиться перезапуски сверх kube-proxy и CNI),
и поведение mesh при потере целой площадки.

Принятое решение и результаты проверки — в ADR 0002. Коротко: service mesh
не вводится, связность даёт Cilium Cluster Mesh, шифрование — WireGuard.

Разрыв «подключение живёт вне GitOps», который ADR предполагал изначально,
**не возник**: обмен сертификатами между кластерами оказался не нужен.
Общий центр сертификации из секрет-бэкенда делает сертификаты взаимно
доверенными, и роль `cilium_bootstrap` раскладывает его сама.

## 5. Gateway API

Закрывает пункт 8 раздела 21.1 («ingress controller или Gateway API») —
последний крупный пункт обязательного списка, который решается на текущем
стенде.

> **Статус: выполнено на стенде `k8s-mtls` по дороге A.** Пройдены все
> позиции 5.5, кроме внешнего анонса адреса LoadBalancer — в облачной VPC
> ни L2-анонсы, ни BGP недоступны, вход снаружи проверен через NodePort.
> Найдено восемь дефектов (51–58 в `docs/TEST-PLAN.md`), из них один клал
> датаплейн на всех узлах, кроме одного, а другой ронял установку на
> чистых ВМ. Всё описано в GitOps; воспроизводимость проверена сносом
> всех объектов и восстановлением из Git. Порядок проверки для людей —
> раздел 6a в `docs/VERIFICATION.md`.

### 5.1. Что изменилось после ADR 0002

Раньше выбор реализации был связан с решением по service mesh: GAMMA даёт
east-west через тот же API, и реализация, умеющая только north-south,
означала бы вторую систему потом. **ADR 0002 mesh не принял**, поэтому
связка распалась: выбор решается доводами ADR 0001 и только ими.

Одновременно закрылся довод против замены kube-proxy: тома только
ReadWriteOnce, поэтому ограничение socket-LB на NFS и SMB не применяется.

### 5.2. Нужно в любом случае

* **CRD Gateway API.** Standard-канал: `GatewayClass`, `Gateway`,
  `HTTPRoute`, `GRPCRoute`, `ReferenceGrant`. Ставятся отдельным
  Application с более ранней sync wave; CRD — cluster-scoped, значит в
  AppProject нужно разрешить `CustomResourceDefinition`.
* **`TLSRoute` — только из experimental-канала, и он ОБЯЗАТЕЛЕН.**
  Проверено на стенде: выбора здесь нет. Оператор Cilium 1.19
  регистрирует тип `TLSRoute` в схеме безусловно, и без его CRD
  контроллер `gateway` на каждой реконсиляции от backend-сервиса выдаёт
  `no kind is registered for the type v1alpha2.TLSRouteList`. То есть
  experimental-канал приходится брать, даже если TLS passthrough не
  используется. Раньше здесь стояло «без его CRD Cilium молча отключает
  поддержку» — это неверно.
* **cert-manager** для сертификатов Gateway. Уже описан в GitOps, но на
  новых кластерах не синхронизирован.

### 5.3. Две дороги

**A. Gateway API от Cilium.** Новых компонентов не добавляет —
`cilium-envoy` уже развёрнут. Требует `kubeProxyReplacement=true`, то есть
смены датаплейна: разрыв установленных соединений при переводе каждого
узла, зависимость от прямого адреса apiserver, отсутствие быстрого отката.
Порядок и проверки — раздел 6 ADR 0001.

Предусловие ADR 0001 на текущем стенде **не выполнено**: в каждом кластере
один control-plane и балансировщика нет, поэтому `k8sServiceHost` указывал
бы на единственный узел. Для проверки механики это приемлемо, для выводов
о production — нет.

**B. Независимая реализация** — Envoy Gateway или NGINX Gateway Fabric.
Датаплейн не трогает, откат — удаление Application. Плата: второй data
plane рядом с `cilium-envoy` и раздвоенная диагностика (L3/L4 через
Hubble, L7 через второй контроллер).

### 5.4. Порядок

1. Развернуть CRD Gateway API standard-канала **и `TLSRoute` из
   experimental** (см. 5.2 — вопрос «нужен ли» снят проверкой) и
   cert-manager через GitOps.
2. Выбрать дорогу A или B. При A — сначала отдельным изменением замена
   kube-proxy, затем отдельным Gateway API; совмещать нельзя, иначе при
   отказе неясно, что сломалось.
3. Поднять `Gateway` и `HTTPRoute` на тестовое приложение, проверить вход
   снаружи и завершение TLS.
4. Проверить, что вывод узла и обновление переживают наличие Gateway.

### 5.5. Что проверять

| Что | Чем |
| --- | --- |
| `GatewayClass` принят | статус `Accepted` у реализации |
| `Gateway` получил адрес | `status.addresses` не пуст |
| маршрутизация | запрос снаружи доходит до приложения по пути из `HTTPRoute` |
| TLS | сертификат выпущен cert-manager и предъявляется Gateway |
| при дороге A | доступ к API **изнутри пода** после смены датаплейна (дефект 35) |

## 6. Идентичность рабочих нагрузок: Cilium mutual authentication — проверено

Механизм проверен на отдельном кластере, включая отказной путь политики и
поведение при отказе SPIRE. Результаты — в `TEST-PLAN.md`, раздел 5.11.
Коротко: работает, запрещает кого надо, отказ SPIRE валит только новые
идентичности, возврат лечит сам.

Срок жизни кеша измерен: при TTL сертификата в 2 минуты трафик работавшей
пары встал через 81 секунду после падения SPIRE, возврат сервера
восстановил его за 46 секунд без вмешательства. Запас времени определяется
сроком жизни сертификата — это ручка компромисса между устойчивостью к
отказу SPIRE и временем жизни скомпрометированного сертификата.

Осталось: работа через границу кластеров (раздел 6.4).



**Это пересмотр ADR 0002, раздел 3.1.** Там mesh не был принят, потому что
требований к идентичности сервисов не заявлялось. Требование появилось —
сработало записанное условие пересмотра.

### 6.1. Что именно берём и чего это НЕ даёт

Cilium mutual authentication проверяет идентичность рабочих нагрузок через
SPIFFE/SPIRE и включается **в правиле политики**:
`authentication.mode: required` в `CiliumNetworkPolicy`.

Чего ждать не надо: это **не** классический per-connection mTLS. Их
собственная документация описывает механизм как вынесенный за пределы
соединения — рукопожатие происходит отдельно, а конфиденциальность
обеспечивает не TLS на соединение, а WireGuard или IPsec.

Если требование звучит как «каждое соединение — отдельная TLS-сессия с
сертификатом рабочей нагрузки, и это показывают аудитору», mutual
authentication его не закрывает; тогда нужен Istio, и это другое решение
с другой ценой.

### 6.2. Предусловия

| Что | Состояние |
| --- | --------- |
| прозрачное шифрование включено | **есть**: WireGuard, проверен дампом |
| сервер SPIRE | роль `spire_server` написана, **на живом сервере не проверялась** |
| агенты SPIRE в кластерах | нет; ролью не покрыты |
| записи регистрации для Cilium | нет; создаёт оператор Cilium через админский сокет агента |
| понимание, что механизм beta в 1.19 | принимается осознанно |

**Собственный сервер вместо встроенного в чарт.** Чарт Cilium умеет
поставить SPIRE сам (`install.enabled`), но такой сервер живёт внутри
кластера, требует PVC и генерирует собственный CA. Для двух кластеров это
означало бы два независимых центра сертификации — и межкластерная
аутентификация стала бы невозможна без федерации. Отдельный сервер на все
кластеры эту задачу снимает.

**Направление обращений, влияющее на сетевые доступы.** Аттестатор
`k8s_psat` проверяет токен узла обращением к apiserver ТОГО кластера. То
есть сервер SPIRE ходит в кластеры, а не только кластеры к нему: серверу
нужен kubeconfig каждого кластера и доступ в эту сторону.

### 6.3. Порядок

0. Развернуть сервер SPIRE (`playbooks/90-spire-server.yml`) и **проверить
   его на живом сервере** — роль написана, но ни разу не выполнялась.
   Затем развернуть агентов в кластерах: ролью они не покрыты, а без них
   рабочие нагрузки идентичностей не получат.
1. Включить на **одном** кластере: `authentication.enabled`,
   `authentication.mutual.spire.enabled`,
   `authentication.mutual.spire.install.enabled`. Перезапустить оператор
   и агенты.
2. Проверить, что SPIRE поднялся и агенты зарегистрировались.
3. Написать `CiliumNetworkPolicy` с `authentication.mode: required` на
   тестовую пару сервисов. Убедиться, что разрешённое ходит.
4. **Проверить отказной путь**: снять у клиента признак, по которому его
   пускают, и убедиться, что соединение действительно не проходит.
   Без этого шага проверка ничего не стоит — политика, которая ничего не
   запрещает, выглядит работающей.
5. Только потом включать на втором кластере.

### 6.4. Открытый вопрос, требующий проверки до внедрения

**Работает ли mutual authentication ЧЕРЕЗ границу кластеров.** Идентичности
между кластерами синхронизируются, но доверие SPIFFE строится на домене
доверия, и для двух независимых SPIRE понадобится либо общий домен, либо
федерация. На стенде это проверяется дёшево: политика с
`authentication.mode: required` на глобальный сервис и обращение из
соседнего кластера.

Пока это не проверено, планировать mutual authentication как
межкластерный механизм нельзя — только как внутрикластерный.

### 6.5. Что проверять

| Что | Чем |
| --- | --- |
| SPIRE работает | под сервера в `Running`, агенты зарегистрированы |
| политика пропускает | разрешённый клиент получает ответ |
| политика **запрещает** | неразрешённый клиент не проходит — обязательный шаг |
| через границу кластеров | обращение из соседнего кластера к глобальному сервису под той же политикой |
| цена | накладные расходы на установление соединений под нагрузкой |

## 7. Регламент обновления ОС на узлах кластера

Доставка пакетов ОС через реестр контура сделана и проверена (раздел 5.12c
в `TEST-PLAN.md`): узлы берут архив Ubuntu и обновления безопасности из
`proxy-ubuntu-archive` и `proxy-ubuntu-security`, установка проходит при
отрезанных прямых путях к архивам. **Регламента самого обновления нет** —
есть только механизм доставки.

### 7.1. Почему это не серия `upgrade/*`

`upgrade/*` обновляет **Kubernetes**: сверяет матрицу совместимости,
переключает apt-репозиторий на нужную ветку, гоняет `kubeadm upgrade`.
Обновление ОС — другое: оно трогает ядро, systemd, libc и containerd, то
есть то, на чём Kubernetes стоит, и требует перезагрузки. Совмещать
нельзя по той же причине, по которой в разделе 5 замена kube-proxy и
Gateway API вносились отдельными изменениями: при отказе будет неясно,
что именно сломалось.

### 7.2. Что должен покрыть регламент

* **Удержание пакетов Kubernetes.** `kubelet`, `kubeadm`, `kubectl` и
  `containerd` не должны обновиться попутно: их версии определяет матрица
  совместимости, а не то, что оказалось свежим в архиве. Нужен явный
  `apt-mark hold` и проверка, что он стоит, — иначе `apt upgrade` тихо
  сменит версию kubelet и разъедется с control plane.
* **Порядок узлов.** По одному, `serial: 1`, с `drain` и `uncordon`.
  Control-plane — последним: пока он обновляется, кластером управлять
  нечем. На стенде control-plane один, поэтому его перезагрузка означает
  полную недоступность API, и это надо проверить отдельно.
* **Перезагрузка.** Обновление ядра без неё не действует, а
  `/var/run/reboot-required` — единственный надёжный признак того, что
  она нужна. Автоматическая перезагрузка всех узлов подряд недопустима:
  нужен барьер по готовности предыдущего.
* **Взаимодействие с `PodDisruptionBudget`.** PDB (раздел 1.2) может
  заблокировать `drain` — и это его работа. Регламент обязан отличать
  «заблокировано осмысленно» от «зависло», иначе первый же прогон
  закончится `--force` и потерей нагрузки.
* **Что делать с etcd.** На узле control-plane перезагрузка означает
  временную потерю члена кворума. При трёх узлах это штатно, при одном —
  простой; регламент должен это различать и отказываться работать, если
  кворум не переживёт вывод узла.

### 7.3. Ловушки, уже известные по этому проекту

Их стоит учесть заранее, а не находить заново:

* `serial` вместе с `run_once` выполняет задачу **на каждом батче**, а не
  один раз за прогон (дефект 32);
* после смены датаплейна или перезапуска узла доступ к API проверяется
  **изнутри пода**, а не с хоста: с хоста `kubectl` ходит на адрес узла
  напрямую и отказ не виден (дефект 35);
* обработчики Ansible срабатывают в конце play — проверка, поставленная
  раньше, увидит старое состояние (дефекты 39, 47 и правки в
  `os_prepare`);
* агент Cilium читает `cilium-config` только при старте, а порядок
  «оператор → агенты» принципиален (дефект 51).

### 7.4. Открытый вопрос

Чем перезагружать: playbook по требованию оператора или оператор в
кластере (kured и подобные). Второе снимает ручную работу, но добавляет
компонент, который сам решает, когда перезагрузить узел, — на площадке с
жёстким окном обслуживания это неприемлемо. Решать до реализации.

### 7.5. Что проверять

| Что | Чем |
| --- | --- |
| пакеты Kubernetes не тронуты | версии `kubelet`/`containerd` до и после совпадают |
| нагрузка пережила | приложение отвечает во время всего прогона |
| `drain` уважает PDB | при одной реплике вывод **блокируется**, при двух проходит |
| перезагрузка учтена | ядро сменилось, `/var/run/reboot-required` исчез |
| кластер цел | узлы `Ready`, кворум etcd, доступ к API **изнутри пода** |
| отказной путь | узел, который не вернулся, останавливает прогон, а не пропускается |
