# План дальнейших работ

Что делать дальше, в каком порядке и почему именно в таком. Состояние
проверенного — в `TEST-PLAN.md`, решения по спорным развилкам — в `adr/`.

---

## 0. Воспроизведение стенда с нуля

Требуется **семь** ВМ, Ubuntu 24.04: по три на кластер в двух разных
подсетях и одна под секрет-бэкенд.

| Роль | Кол-во | Ресурсы |
| ---- | ------ | ------- |
| control-plane | 1 на кластер | 4 vCPU / 4 ГБ / 20 ГБ |
| worker | 2 на кластер | 4 vCPU / 4 ГБ / 20 ГБ |
| OpenBao | 1 | 2 vCPU / 2 ГБ / 20 ГБ |

Сети: подсети кластеров должны видеть друг друга; между узлами разных
кластеров нужны **UDP 51871** (WireGuard) и **TCP 32379** (NodePort
`clustermesh-apiserver`). ВМ с OpenBao должна быть доступна **с
управляющей машины** по 8200: lookup выполняется там, а не на узлах.

### 0.1. Что автоматизировано

* установка кластеров — `site.yml`;
* раскладка общего CA из секрет-бэкенда — роль `cilium_bootstrap`;
* подготовка стенда — `00-stand-prerequisites.yml`;
* разбор стенда — `99-stand-teardown.yml`.

### 0.2. Что делается руками — и это разрыв

Ниже перечислено то, для чего роли **не написаны**. Пока эти шаги
выполняются вручную, «воспроизвести с нуля одной командой» не получится.

1. **Развёртывание OpenBao.** Установка пакета, TLS-сертификат с нужными
   SAN, `bao operator init`, распечатывание, включение KV v2 на `kv/`.
2. **Генерация общего CA** для Cluster Mesh и запись его в бэкенд вместе
   с ключами шифрования etcd каждого кластера по путям
   `kv/kubernetes/<cluster_name>`.
3. **Локальные файлы инвентаря** — `hosts.local.yml`,
   `group_vars/all/99-local.yml` с адресами, `openbao_ca_cert`. В git не
   попадают намеренно.
4. **Адреса соседнего кластера** в `clustermesh.config.clusters` values
   Cilium — их знает только тот, кто поднял ВМ.
5. **Переменные окружения** управляющей машины:
   `ANSIBLE_HASHI_VAULT_TOKEN` и `ANSIBLE_HASHI_VAULT_CA_CERT`. Роли
   вызывают lookup только с `url`, поэтому иначе первый же прогон падает
   на `CERTIFICATE_VERIFY_FAILED`.

**Что стоит автоматизировать в первую очередь** — пункты 1 и 2: роль
`openbao` и playbook начальной загрузки секретов. Тогда воспроизведение
сведётся к «поднять ВМ, вписать адреса, запустить два playbook».

### 0.3. Порядок

1. Поднять семь ВМ, проверить связность между подсетями и доступность
   8200 с управляющей машины.
2. Развернуть OpenBao, сгенерировать общий CA, разложить секреты.
3. Заполнить локальные файлы инвентарей обоих кластеров.
4. `00-stand-prerequisites.yml` для каждого кластера.
5. `site.yml` для каждого кластера.
6. Вписать адреса соседа в values Cilium обоих кластеров, применить
   `50-cni-bootstrap.yml`.
7. Проверить mesh: `cilium-dbg status --all-clusters` и переезд
   глобального сервиса между кластерами.

**Важно:** OpenBao после перезапуска своей ВМ запечатывается и требует два
ключа из трёх. Без него не проходит preflight обоих кластеров. Ключи
распечатывания и корневой токен хранятся у оператора.

## 1. Дешёвое и ни от чего не зависящее

Делается на текущем стенде, внешних условий не требует.

### 1.1. Шифрование трафика WireGuard

Одно значение в values Cilium. Закрывает частое требование «трафик
шифруется в транзите» **без** service mesh, без ADR по нему и без второго
кластера.

Проверка: снять трафик между узлами и убедиться, что он не читается;
`cilium-dbg status` показывает включённое шифрование.

### 1.2. Базовые политики через GitOps

`ResourceQuota`, `LimitRange`, базовые `NetworkPolicy`,
`PodDisruptionBudget`. Чистые манифесты, внешних зависимостей нет.

PDB имеет смысл только теперь, когда worker-узлов два: при одной реплике
`minAvailable: 1` блокирует вытеснение и ломает вывод узла.

### 1.3. etcd-backup CronJob

Документ (раздел 28.1) считает основным механизмом именно CronJob, а
systemd timer — запасным для контуров, где запрещён hostPath. Проверен пока
только запасной. Референсный манифест роль `etcd_backup` уже рендерит в
`/etc/kubernetes/bootstrap/`.

## 2. Регламент на топологии с балансировщиком

Все эти сценарии проверялись, когда endpoint'ом служил адрес узла кластера.
С HAProxy между узлами условия другие.

| Сценарий | Что проверяет именно теперь | Приоритет |
| -------- | --------------------------- | --------- |
| `renew-control-plane-certs` | попадёт ли адрес LB в **перевыпущенные** сертификаты | высокий |
| `add-node` / `remove-node` | появится ли узел в backend'ах HAProxy и уберётся ли выведенный | средний |
| `restore-etcd` | достаточно ли перезапуска kube-proxy и CNI | средний |
| `upgrade/*` | переживёт ли балансировщик поочерёдный перезапуск apiserver | средний |

Продление PKI — первое по важности: `kubeadm certs renew` берёт SAN из
конфигурации кластера, и если `controlPlaneEndpoint` там прописан, всё
сойдётся. Это предположение, а не проверенный факт; ошибка здесь тихо
ломает кластер через год.

## 3. Отказные пути

Все прогоны до сих пор шли по счастливому пути.

| Что | Как |
| --- | --- |
| Проверки `preflight` | подставить заведомо неверные значения и убедиться, что каждая срабатывает |
| Потеря control-plane узла | погасить один; кластер должен жить, HAProxy — увести трафик |
| Потеря балансировщика | погасить; проверить предсказание, что control-plane продолжит работать, а worker-узлы отвалятся |

Последние два дают больше уверенности, чем несколько зелёных прогонов
установки, и стоят минут.

## 4. Мультикластер и шифрование

Решение принято — **ADR 0002**: service mesh не вводится, связность даёт
Cilium Cluster Mesh, шифрование — WireGuard. Требования: связность и
шифрование, без идентичности сервисов и L7-управления между ними.

Порядок из раздела 6 ADR, часть решений необратима после установки:

1. **Проверить режим датаплейна** и зафиксировать туннельный явно в
   inventory. При native routing понадобилась бы маршрутизируемость
   pod-сетей между ДЦ; в туннельном достаточно связности узлов.
2. **Включить WireGuard** на первом кластере (см. 1.1) — это же и
   предусловие расширения mesh: смешанный режим не поддерживается.
3. **Ввести `cluster_id`** и развести PodCIDR/ServiceCIDR по инвентарям.
   Сейчас они заданы одним значением на все; изменить их после установки
   кластера нельзя.
4. **Согласовать ACL**: UDP 51871 между узлами разных кластеров и порты
   `clustermesh-apiserver`. Кластеры в разных VLAN, поэтому это отдельная
   работа с сетевиками, а не деталь установки.
5. **Поднять второй кластер** тем же playbook с собственным inventory.
6. **Соединить кластеры**, проверить `cilium-dbg status --all-clusters` и
   глобальный сервис из обоих кластеров.

Подключение временно живёт вне GitOps: обмен CA и endpoint соседа — секреты
пары кластеров, и до появления OpenBao класть их некуда. Разрыв осознанный
и закрывается вместе с секрет-бэкендом.

## 5. Заблокировано внешними условиями

| Что | Чем заблокировано |
| --- | ----------------- |
| Keepalived и общий VIP | нужна сеть с поддержкой VRRP; в облаке L2-VIP не поднять |
| Gateway API | ADR 0001: требует замены kube-proxy, а та — отказоустойчивого endpoint. GAMMA больше не драйвер: ADR 0002 не принял mesh |
| External Secrets Operator | нужен OpenBao |
| Приватный GitOps по SSH | нужен deploy key и приватный репозиторий |
| Работа через Harbor и внутренние зеркала | нужен закрытый контур |
| Отдельный диск под etcd | нужна ВМ с дополнительным томом |
| `firewall_manage: true` | не включался; риск конфликта с Cilium не проверен |
| Продление **истёкших** сертификатов | сценарий требует отдельной подготовки: apiserver не принимает соединения, `kubeadm` не читает конфигурацию из кластера |

## Порядок

1. Поднять стенд (раздел 0).
2. WireGuard — дёшево и независимо (1.1).
3. Продление PKI на новой топологии (2) — единственное, что может тихо
   сломать кластер через год.
4. Отказные пути (3) — минуты, а уверенности больше, чем от повторных
   установок.
5. Базовые политики и etcd-backup CronJob (1.2, 1.3).
6. Подготовка к мультикластеру (4): режим датаплейна, `cluster_id`,
   разведение CIDR, согласование ACL.
7. Второй кластер и Cluster Mesh (4) — после согласования сети.
