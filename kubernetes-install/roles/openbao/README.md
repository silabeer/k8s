# openbao

Ставит и настраивает OpenBao — секрет-бэкенд проекта (раздел 22 документа).
Закрывает первый из разрывов воспроизводимости, перечисленных в
`docs/PLAN.md`, раздел 0.2.

## Статус

Сама роль на живом сервере **не выполнялась**. Но процедура, которую она
кодирует, выполнена вручную и проверена целиком: установка, TLS,
инициализация, распечатывание, KV v2, чтение секретов ролями проекта через
lookup и проверка доступности из preflight.

Это отличает её от `roles/spire_server`, где не проверено ни то, ни другое.

## Что делает

* ставит пакет нужной версии;
* перевыпускает TLS-сертификат с адресами, по которым к серверу реально
  обращаются, либо принимает готовый от оператора;
* рендерит конфигурацию с `api_addr`;
* запускает службу, инициализирует хранилище, при необходимости
  распечатывает и включает KV v2.

## Грабли, заложенные в роль

Каждая — из ручного прогона, все стоили времени:

* **Имя артефакта** — `openbao_<версия>_linux_amd64.deb`, а не `bao_...`.
  При неверном имени `dpkg` молча ничего не ставит.
* **Сертификат от пакета не содержит нужных SAN.** Пакет генерирует свой
  при установке, но без адресов, по которым к серверу обращаются, и
  подключение падает на проверке имени.
* **Права на сертификат.** Каталог `0700` ломает клиента: `bao status`
  падает с «permission denied» ещё до обращения к серверу, потому что
  тот же файл нужен ему как доверенный корень. Сертификат — `0644`.
* **`api_addr` обязателен**, иначе инициализация завершается ошибкой.
* **KV именно версии 2.** Роли проекта строят путь как
  `<mount>/data/<путь>`; с KV v1 lookup вернул бы пустоту без ошибки.
* **Перевыпуск сертификата условный.** Безусловный менял бы его на каждом
  прогоне и перезапускал службу.
* **`flush_handlers` до работы с хранилищем.** Иначе инициализация пойдёт
  к серверу со старой конфигурацией: обработчик сработал бы в конце play.

## Ключи распечатывания

Выдаются **один раз за всю жизнь хранилища**. Роль сохраняет их на
управляющей машине с правами `0600` и не пишет ни в лог, ни в вывод.
Оператор обязан перенести их в постоянное хранилище и удалить файл.

`openbao_auto_unseal` — удобство **стенда**. Держать ключи рядом с сервером
в production бессмысленно: это равнозначно незапечатанному хранилищу. Там
распечатывают люди либо KMS облака.

В production корневой токен после начальной настройки отзывается, а работа
идёт через AppRole с ограниченной политикой. Роль этого не делает.

## Чего не делает

* не загружает секреты кластеров — это отдельный шаг;
* не настраивает AppRole и политики;
* не обеспечивает отказоустойчивость: хранилище `file` рассчитано на один
  сервер, для пары нужен raft или внешнее хранилище.
