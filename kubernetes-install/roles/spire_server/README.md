# spire_server

Ставит и настраивает **сервер** SPIRE — центр выдачи идентичностей SPIFFE
рабочим нагрузкам. Нужен для Cilium mutual authentication (ADR 0002,
раздел 3.1; план, раздел 6).

## Статус

**Проверена частично.** Установка, конфигурация, служба, `healthcheck`,
выдача корневого сертификата и идемпотентность — прогнаны на живом
сервере. Три ошибки, найденные первым прогоном, исправлены (см. ниже).

**Не проверено: аттестация узлов.** Аттестатор `k8s_psat` требует
настоящих кластеров и их kubeconfig; прогон выполнялся с заглушкой,
поэтому проверена форма конфигурации, а не её работа. До проверки с
живыми кластерами роль нельзя считать готовой к применению.

## Что нашлось первым прогоном

Три ошибки, все написаны вслепую и все найдены на живой машине:

* **DataStore.** Имя плагина — `sql`, а конкретная база задаётся отдельным
  полем `database_type`. Плагина с именем `sqlite3` не существует, и
  конфигурация отвергалась с невнятным «malformed database type
  configuration». Поймано проверкой `spire-server validate` в шаблоне —
  битая конфигурация на сервер не попала.
* **Журнал в файл.** Под `ProtectSystem=strict` запись в `/var/log`
  отвергается, даже когда права на каталоге верные и та же запись от того
  же пользователя из оболочки проходит. Служба уходила в цикл перезапусков.
  Исправлено переводом журнала в journald — на systemd-хосте отдельный файл
  только раздваивает место, куда смотреть.
* **Административный сокет в приватном `/tmp`.** Юнит работает с
  `PrivateTmp`, и сокет по умолчанию оказывался в изолированном
  пространстве имён: снаружи невидим, `healthcheck` сервер не находил,
  хотя тот был полностью здоров и писал в журнал «Serving health checks».
  Путь задан явно вне `/tmp`.

## Что делает

* ставит дистрибутив SPIRE нужной версии;
* заводит системного пользователя и каталоги, ключ CA и база идентичностей
  кладутся в каталог с доступом только службе;
* рендерит конфигурацию с проверкой синтаксиса до записи
  (`spire-server validate`);
* настраивает аттестатор `k8s_psat` на перечисленные кластеры;
* ставит systemd-юнит, запускает и проверяет `spire-server healthcheck`;
* показывает корневой сертификат для передачи агентам.

## Чего НЕ делает

Границы важнее возможностей, поэтому явно:

* **не разворачивает агентов** в кластерах — а без них рабочие нагрузки
  идентичности не получат: `agentSocketPath` в Cilium это локальный сокет
  на узле;
* **не создаёт записи регистрации** для Cilium — их создаёт оператор
  Cilium через административный сокет агента;
* **не включает mutual authentication** в самом Cilium — это values чарта.

## Направление обращений

Неочевидное и влияющее на сетевые доступы: аттестатор `k8s_psat` проверяет
projected-токен узла **обращением к apiserver того кластера**. То есть
сервер SPIRE ходит в кластеры, а не только кластеры к нему. Отсюда
требование kubeconfig каждого кластера на сервере и сетевой доступ в
эту сторону.

## Ограничения

* Хранилище `sqlite3` рассчитано на один сервер. Отказоустойчивая пара
  требует внешнего PostgreSQL и общего datastore — это меняет и схему
  развёртывания, и роль.
* `spire_download_checksum` по умолчанию не задан. Перед production
  закрепить: иначе дистрибутив берётся без проверки целостности.
* Домен доверия меняется только вместе с переизданием всех идентичностей.
  Для межкластерной аутентификации он обязан совпадать во всех кластерах,
  и сервер должен быть один — два независимых сервера с одинаковым именем
  домена доверия друг другу не создают.
